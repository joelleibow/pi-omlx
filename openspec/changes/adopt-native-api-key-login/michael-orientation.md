**ADR 0001** (`docs/adr/0001-one-credential-decides-the-omlx-connection.md`) records the credential ruling. Two of its premises are measurable facts about pi, not rulings, and this change tests both (see traps iii and vi): "pi's answer is not readable at the moments that matter", and "the extension's resolution is a copy of pi's". The ADR itself says what is protected: "Changing this record's mind means changing which credential wins, not where the code lives." Moving the resolution into a pi-invoked hook is permitted; changing the order (stored first, env only when nothing is stored) is not.

**Living specs this change moves or must keep**: `credential-resolution` (will be revised: several scenarios name the oauth record shape and the registration fields `apiKey: "$OMLX_API_KEY"` / `authHeader`), `provider-access` (keep), `diagnostics` (keep the `provider_registered` `source` line), `environment-configuration` (keep), `test-isolation` and `verification` (keep; new env keys or paths go to `CALLER_ENV_KEYS` and the guard), `catalog-discovery` (keep unless Joel widens scope, question A).

## 2. What this change must not touch

- Which credential wins. pi-ai's own order is the same rule (`pi-ai/dist/auth/resolve.js:25-37`: a stored credential owns the provider; ambient env only when nothing is stored), so the native path can satisfy the ruling. But pi hands the stored credential to the *provider's* `resolve()` and lets the provider merge per field: llama does `credential?.key ?? ctx.env("LLAMA_API_KEY") ?? "local"` (`extensions/llama/provider.js:123`). Copying that line would let `OMLX_API_KEY` reach a saved keyless login, which the ruling and the spec scenario "A stored credential with an empty key registers keyless while `OMLX_API_KEY` is set" forbid. The omlx `resolve()` must read env only when `credential` is undefined.
- `OMLX_BASE_URL` alone stays unconfigured (ruling + ADR), even though a native `resolve()` could now make it work (question C).
- The extension never writes `auth.json`; storing a login is pi's job (`Models.login` persists through `credentials.modify`, `pi-ai/dist/models.js:382-386`). So there is no in-extension migration of existing oauth-shaped records (question B).
- Provider id `omlx`; `PROVIDER_KEY` as its one home; credentials keyed `omlx`.
- The isolation contract: new fixtures reach pi's state through `PI_CODING_AGENT_DIR`; no `tmpdir` outside `test/isolation/global-setup.ts`; no suppressions.
- The stream wrapper (`src/stream.ts`) and thinking controls: unrelated to auth. A native `Provider` must still route `streamSimple` through `streamOmlxOpenAICompletions`.
- The three startup/notice rulings, unless Joel widens scope (question A).

## 3. Traps visible at HEAD, each measured

**i. "As pi intends" is a different `registerProvider` overload, not a field on `ProviderConfig`.** `ProviderConfig.oauth` is the only login hook on the name+config overload (`core/extensions/types.d.ts:1495-1512`); its `apiKey` string yields a *fabricated* "Enter API key" prompt with no URL step (`core/provider-composer.js:254-258`). The URL+key API-key login llama uses is `Provider.auth.apiKey.login` (`pi-ai/dist/auth/types.d.ts` `ApiKeyAuth`), reachable from an extension through `registerProvider(provider: Provider)` (`types.d.ts:1403`; `core/extensions/loader.js:371-379` → `runtime.registerNativeProvider`, `core/model-runtime.js:642-651`). A native provider is used untouched unless `models.json` has an `omlx` entry (`model-runtime.js:157-163`). It must supply `getModels`, `stream`, `streamSimple` and `auth` itself (`pi-ai/dist/models.d.ts:72-127`); `ProviderConfig`'s `baseUrl`/`apiKey`/`authHeader`/`models` composition no longer applies, so `src/provider.ts`'s `toProviderConfig` and the spec's `apiKey: "$OMLX_API_KEY"`/`authHeader` scenarios go with it.

**ii. The native login does not fetch the catalog; pi does, after persisting.** Today's design fetches inside `login()` because "pi calls modelRegistry.refresh() synchronously right after login() resolves, before credentials even reach storage" (`src/oauth-login.ts:4-13`, `index.ts:167-171`, `index.ts:285-291`). On 1.5.2 that premise is false: `Models.login` persists the credential (`pi-ai/dist/models.js:375-405`), then `completeProviderAuthentication` runs `refresh({ providers: ["omlx"] })` with network and a 15 s timeout (`modes/interactive/interactive-mode.js:5269-5272`), which calls the provider's `refreshModels` with the resolved credential (`pi-ai/dist/models.js:168-178, 200-205`). Consequence for the design: if omlx has no `refreshModels`, nothing fetches after a login until the extension's own poll ticks, and the unconfigured poll is in 2 s→60 s backoff (`index.ts:33-35, 160-163`), so a login could show no models for up to a minute. The three other times pi refreshes catalogs with network: once after interactive init (`interactive-mode.js:863-869`), when `/model` opens (`:4682`), and on an unknown model reference (`:4491`). Pi has no periodic refresh (no `setInterval`/`checkedAt` scheduling in `model-runtime.js`, `models-store.js` or `pi-ai/dist/models.js`).

**iii. Keyless chat is already broken at HEAD on 1.5.2.** Measured: composing today's registration with pi's composer and calling `auth.oauth.toAuth` on a keyless record returns `{"apiKey":""}` (`scratch-michael/keyless-toauth.mjs`); `Models.applyAuth` forwards `""` (`pi-ai/dist/models.js:447`); the extension's wrapper delegates to `openAICompletionsApi().streamSimple`, whose `getClientApiKey` throws `No API key for provider: omlx` for `""` or `undefined` before any request (`pi-ai/dist/api/openai-completions.js:35-41, 182`; `scratch-michael/keyless-stream.mjs` output: `"" -> No API key for provider: omlx`, `undefined -> same`, `"local" -> Connection error`). The spec's keyless scenarios check the catalog fetch and the registration shape only, so the suite stays green while chat on a keyless login fails. Pi's own answer is llama's sentinel `?? "local"`, which sends `Authorization: Bearer local`. Whether oMLX with `skip_api_key_verification` accepts an arbitrary bearer is **unchecked** (no live server was probed); it is the one runtime fact the design needs from research before it can say what "keyless" means on the wire.

**iv. Existing oauth-shaped logins become "not configured" after the change.** `resolveProviderAuthWithSignal` returns `undefined` for a stored `oauth` record when the provider has no `auth.oauth` (`pi-ai/dist/auth/resolve.js:25-33`), and `resolveRefreshCredential` does the same (`models.js:244-248`). Joel's own saved login, and anyone else's, stops working silently until `/logout` + `/login`. The extension cannot rewrite the record (it never writes `auth.json`). Question B.

**v. The native keyless record has no `key`.** llama returns `key: apiKey || undefined` and `JSON.stringify` drops it, so the stored record is `{ type: "api_key", env: { ...BASE_URL } }`; pi's reader accepts `key` undefined (`core/auth-storage.js:193-201`). Today's resolver treats an `api_key` record without a key as *not configured* (`src/config.ts:49-50`), and the spec scenario "A stored api_key with an empty key is not configured" enshrines that. The native keyless shape contradicts that scenario; the design must revise it, not keep both.

**vi. ADR 0001's "not readable" premise is half stale.** `ctx.modelRegistry.getProviderAuth(provider)` exists on every event context (`core/model-registry.d.ts:51`), but the factory where the poll starts has no `ctx`. With a native provider the resolution lives in `auth.apiKey.resolve` and pi calls it; the `shortcut:` mirror comment in `src/config.ts:36` and `AGENTS.md`'s trap about it go away. Anything that still resolves the credential outside pi's calls (today's poll, `index.ts:264, 278`) is a second resolution path the ADR was written to prevent; the design should have one.

**vii. The `api_key` key is interpolated on read.** `AuthStorage.read` runs `resolveConfigValue(key, env)` on `api_key` records (`core/auth-storage.js:221-224, 380-384`): a typed key beginning with `$` or `!` is an env reference or a command. The ADR already records this as a consequence; it moves from the fabricated path to the main path, so the docs pass should say so.

**viii. Test fakes are built on the name+config overload.** `test/index.test.ts` fakes `registerProvider(provider: string, config)` (`:53, :202`), drives login through `lastRegistered()?.oauth?.login` (`:87, :441, :459, :861`), and `test/config.test.ts`, `test/auth-storage.test.ts`, `test/oauth-login.test.ts` fix the oauth record shape. The fake pi must accept a `Provider` and drive `auth.apiKey.login`/`resolve`/`refreshModels` with an `AuthContext` whose `env` is the test's, or every wiring assertion is on a shape the code no longer produces. Any new `process.env` key goes to `CALLER_ENV_KEYS` (`test/isolation/global-setup.ts:14-20`).

**ix. Stale labels, documentation only.** `index.ts:162-164` says "Use a subscription"/"Use an API key"; 1.5.2's selector says "Sign in with an account"/"Sign in with an API key" (`interactive-mode.js:5067-5068`). README already uses the new words. `docs/CONFIGURATION.md:7` promises an `oauth`-typed record and `:46` promises keyless works; both become false. Minor, for Bambadjan's docs pass.

## 4. Questions that are Joel's (`owner: joel`)

**A. Scope: auth only, or pi's catalog lifecycle too?** The native `Provider` shape couples two things the ruling names only one of. Options: (1) *Auth plus pi's post-login hook*: `auth.apiKey.{login, resolve}` and a `refreshModels` that fetches with `context.credential` and publishes the list; keep the extension's own poll, `cache/omlx-models.json` and the three notice rulings untouched; put "adopt pi's `models-store.json` and drop the poll" on the board as its own card. (2) *Auth plus pi's whole catalog lifecycle*: `refreshModels` with `context.stored`/`publish({ persist })` replaces the poll, the backoff, the extension's cache and most of the notice code; pi already refreshes at init, after login and on `/model` without blocking startup, but it never refreshes periodically, and the "one notice per session" rulings would be revisited. (3) *Auth only, no `refreshModels`*: smallest, but a login shows no models until the backed-off poll ticks (trap ii). **I would choose (1)**: it is the narrow correction the ruling asks for, it fixes the post-login gap pi created, and it leaves each startup/notice ruling to be revisited on its own evidence rather than as a side effect.

**B. Upgrade behaviour for a saved oauth-shaped login.** Options: (1) clean break: the old record resolves as not configured; the login-only state's message and the docs tell the user to `/logout` and `/login` again; (2) keep `auth.oauth` registered as a legacy reader so old logins keep working, which shows OMLX under both "Sign in with an account" and "Sign in with an API key" indefinitely and contradicts "as pi intends"; (3) the extension rewrites the record, which breaks "never writes `auth.json`" (ADR 0001, and `AGENTS.md`'s trap). **I would choose (1)**; the known user base is Joel, and the message at `index.ts:242` already names the remedy. He should rule because it is his saved login that stops working on upgrade.

**C. Keyless on the wire.** Today's spec promises "no Authorization header" for a keyless catalog fetch, and the docs promise keyless chat works; chat has never worked on 1.5.2 (trap iii). Pi's own precedent is a sentinel bearer. Options: (1) follow llama: resolve a placeholder key when the saved login has none, send `Bearer <placeholder>` on catalog and chat alike, and revise the spec's "no header" wording — valid only if research measures that oMLX's `skip_api_key_verification` ignores the header; (2) keep "no header" and bypass `getClientApiKey` in the extension's stream wrapper, which is new mechanism against a pi internal. **I would choose (1) if the measurement passes**, and bring (2) back to Joel only if it fails. The ruling "a keyless server is reached by login with an empty key" stands either way; this question is about whether Joel accepts the wire change, and it tells him the keyless promise is currently broken.

**D. (Narrow, derived from B/C.)** Env-only keyless stays unsupported by ruling. A native `resolve()` removes the reason the ruling gave ("pi treats the provider as not configured"); I recommend keeping it unsupported in this change and recording that the premise changed, so Joel can reopen it on its own card if he wants. No decision needed now unless he wants to widen scope.
