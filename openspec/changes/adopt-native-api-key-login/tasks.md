# Tasks

Tasks marked *(structure)* change shape without changing behaviour; they are verified by the suite staying green and by the named search returning nothing. Tasks marked *(guard)* are green from the start and name the mutation that turns them red. Every other task starts with a failing test whose name is given, lands the code that makes it pass, and names its boundary cases. Each task cites the design decision and the spec requirement it builds; `design.md` and `specs/` are the contract.

## 1. The credential resolution

Lands `credential-resolution`: "Pi's Resolve Decides The Base URL, The Key And Keyless-ness", "A Keyless Login Sends A Placeholder Bearer", "A Base URL Alone Stays Unconfigured". Designs D3, D4.

- [x] 1.1 *(structure)* The fake pi's `registerProvider` records the object when it is given a `Provider` and keeps the string overload for now, so `test/index.test.ts`'s existing helpers still answer. - [x] 1.2 A stored `api_key` credential decides the URL and the key through `resolveOmlx`, whose answer is `{baseUrl, apiKey, source}`, and the environment is consulted for neither (D3; "A stored credential outranks both environment variables"). Failing test first in `test/config.test.ts`: "resolveOmlx returns the stored URL and key while both variables are set". Boundary cases: only `OMLX_BASE_URL` set, only `OMLX_API_KEY` set — with a stored credential, neither changes the answer. How pi receives that answer as `auth` and `env` is 4.2's.
- [x] 1.3 A stored credential with no key resolves the placeholder and counts as configured (D3, D4; "A stored login with no key stays keyless while the environment key is set", "A keyless login is configured"). Failing test: "resolveOmlx returns the placeholder for a stored credential with no key while OMLX_API_KEY is set". Boundary case: a stored `key: ""` — the input on which `||` and `??` differ, and the one that would send an empty bearer.
- [x] 1.4 A stored credential with no base URL takes `DEFAULT_OMLX_BASE_URL` while `OMLX_BASE_URL` names another server (D3; "A stored credential without a base URL takes the default"). Failing test: "resolveOmlx falls back to the default URL for a stored credential with no base URL".
- [x] 1.5 With nothing stored, both halves come from the environment; with no environment key the credential is unconfigured, and `OMLX_BASE_URL` alone is unconfigured too (D3; "The environment supplies both halves when nothing is stored", "Nothing stored and nothing set is unconfigured", "A base URL alone makes no catalog fetch"). Failing test: "resolveOmlx reads both halves from the environment and reports nothing for a URL alone". Boundary cases: URL only, key only, neither.
- [x] 1.6 *(structure)* `resolveOmlxCredential` and the `shortcut:` mirror comment in `src/config.ts` are deleted, every call site now goes through `resolveOmlx`, and `normalizeBaseUrl` with its tests stays. ## 2. The refresh hook

Lands `catalog-discovery`: "Pi's Refresh Decides When The Catalog Is Fetched", "A Session Start Waits For No Network Fetch", "The Catalog Lives In Pi's Model Store", "A Refresh That Is Superseded Or Aborted Publishes Nothing"; and `credential-resolution`: "The Catalog And Chat Share The One Resolution". Designs D2, D7, D13.

- [x] 2.1 *(structure)* `registrableModels` lives in `src/catalog.ts` and takes `OmlxModel[]`; the call sites that filtered inline — the network fetch and the probe that lands in 3.4 — go through it (D7). Verified by `npm run check` green and `rg -n 'isRegistrableModel' src` reporting nothing.
- [x] 2.2 The offline phase publishes the catalog pi stored and makes no request (D7 step 1; "A session start restores the stored catalog without a network request", "A start reads the store, not a cache of the extension's"). Failing test: "the offline phase publishes the stored models and fetches nothing", driving `refreshOmlxCatalog` with a recording `publish` and a fetch spy that fails the test if called. Boundary case: an empty store publishes an empty list and throws nothing. The three "A session start waits for no network fetch" scenarios describe pi's phase sequencing — pi awaits this phase before the session exists and runs the network phase afterwards (`agent-session-services.js:111`) — so the extension's part in them is that this phase is request-free, asserted here, and that `refreshModels` is on the registered provider, asserted in 4.4.
- [x] 2.3 The network phase publishes through `persist` and the update (D7 step 2; "A successful network refresh persists under omlx"). Failing test: "the network phase publishes the fetched models with persist". Boundary case: a credential that is absent, is not `api_key`, is keyless, or carries no `env.OMLX_BASE_URL` throws an error naming the missing piece, with no fetch and no publish (D7, D13). This boundary changes an existing test's expectation deliberately, as 3.8 changed the login's failed-fetch expectation for ruling C2: `test/refresh.test.ts`'s "returns without fetching or throwing" case is rewritten to expect the throw as part of this design amendment, and the red it is written from is the current silent return, not an expectation edited to fit.
- [x] 2.4 The published model is a complete pi `Model`: `provider` is `omlx`, `api` is `openai-completions`, and `baseUrl` is the URL the refresh fetched from (D7 "The published shape"; "The published models are selectable"). Failing test: "the published model carries provider omlx, api openai-completions and the fetch URL as baseUrl". Boundary case: `reasoning` is true only when the catalog's `thinking_default` is true. This is the task that catches an unchanged `toProviderModel`: every other test in this list passes while publishing a model pi never lists.
- [x] 2.5 The network phase filters before it maps: a response holding one model with positive context and output limits and one without publishes the one and skips the other (D7; "A response with one model lacking limits publishes the rest"). Failing test: "a mixed response publishes the registrable model and skips the limit-less one". Boundary case: only a limit-less model — 2.6's case, not this one. This is the input that makes filter-first and map-first differ: mapping first throws and publishes nothing.
- [x] 2.6 A response with no registrable model throws before any publish, and the message names the endpoint and the count (D7, D13; "A failed refresh keeps the stored catalog"). Failing test: "no registrable model throws and leaves the store and the published list unchanged". The error is what pi records in `ModelsRefreshResult.errors`, so the failure is traced under `PI_OMLX_DEBUG` (logging: the adapter records the call and its outcome).
- [x] 2.7 The extension forwards `context.signal` to `fetchModels` and commits the list only inside `update`, so a publish pi rejects leaves `getModels()` unchanged (D2, D7; "An aborted refresh publishes nothing", "A superseded refresh publishes nothing"). Failing test: "the fetch receives context.signal and a publish that resolves false without running update leaves getModels unchanged". Boundary case: the signal is already aborted before the fetch — no request is made and nothing is committed.
- [x] 2.8 The refresh takes its URL and key from what `resolve` returned and never reads `OMLX_API_KEY` at fetch time (D3, D7; "The refresh and the request carry the same URL and key", "No second resolution at fetch time", "The catalog request carries the placeholder bearer", "A keyed login sends its own key"). Failing test: "the fetch carries the stored key while OMLX_API_KEY names a different one". Boundary case: a stored keyless login while `OMLX_API_KEY` is set — the placeholder goes out, not the environment key.

## 3. The login

Lands `native-login`: "The Login Asks For A Base URL And An Optional Key", "The Login Returns The Credential Pi Stores", "The Login Leaves The Catalog To Pi", "The Login Probes The Server Before It Saves". Designs D4, D5, D6, D13.

- [x] 3.1 *(structure)* `src/oauth-login.ts` becomes `src/login.ts` and `test/oauth-login.test.ts` becomes `test/login.test.ts`; the exports stay as they are until 4.4 deletes the OAuth-only ones with their last caller (D5, D12). Verified by `npm run check` green and `rg -n 'oauth-login' src test` reporting nothing.
- [x] 3.2 The login prompts for a base URL and then for a key that may be empty, normalizes the URL to end in `/v1`, and returns an `api_key` credential whose `key` is omitted when none was entered (D5; "A login with a key", "A login with an empty key", "A URL without `/v1` gains it"). Failing test: "loginOmlx prompts for the URL then the key and returns an api_key credential". Boundary cases: a URL already ending in `/v1`, a URL with trailing slashes, a whitespace-only key treated as no key.
- [x] 3.3 A blank base URL fails the login before any request is made (D5, D13; "A blank base URL is rejected"). Failing test: "loginOmlx rejects an empty base URL without fetching". Boundary case: a whitespace-only URL.
- [x] 3.4 The probe fetches once with the credential the login is about to return, publishes nothing and registers nothing (D6; "A reachable server lets the login finish", "The probe publishes nothing", "A login publishes nothing"). Failing test: "loginOmlx fetches with the credential it is about to return and neither publishes nor registers". The spy fails the test on any publish or registration, which is how this catches a login that registers the way today's does.
- [x] 3.5 An unreachable server, a rejected key and a catalog with no registrable model each fail the login with a message naming the cause and store nothing (D6, D13; "An unreachable server fails the login", "A rejected key fails the login", "A catalog with no registrable model fails the login"). Failing test: "loginOmlx fails with the cause when the fetch throws". Boundary cases: a 401 from a server that requires a key; a 200 with zero models.
- [x] 3.6 A catalog with one unusable model still lets the login finish, and a keyless probe sends the placeholder bearer (D4, D6; "A catalog with one unusable model still lets the login finish", "A keyless probe sends the placeholder bearer", "A keyless server is configured by a login"). Failing test: "a mixed catalog lets the login finish and the keyless probe carries the placeholder". Boundary case: every model unusable — 3.5's failure.
- [x] 3.7 The probe honours the interaction's signal: an abort during the fetch stops it and fails the login without storing anything (D6; "The probe honours the interaction's signal"). Failing test: "an aborted interaction fails the login and stores nothing". Boundary case: the signal already aborted before the fetch starts.
- [x] 3.8 The login returns exactly what pi stores — an `api_key` credential carrying the prompted URL — the extension writes nothing to `auth.json`, and a failing post-login refresh leaves the stored credential in place (D5; "The stored entry is api_key-typed", "A keyless login stores no key", "The extension writes nothing to auth.json", "A failed refresh keeps the credential"). Failing test: "the login leaves auth.json byte-identical outside the omlx entry, and a failing refresh keeps it". Fixture under `inject("isolationRoot")` with `PI_CODING_AGENT_DIR` pointing at it.

## 4. The provider object and the registration flip

Lands `native-login`: "The Extension Declares A Native API-Key Login"; `catalog-discovery`: "No timer refreshes the catalog", "The published models are selectable", "The Extension Never Chooses The Session's Model". Designs D1, D2, D12.

- [x] 4.1 `getModels()` serves the list the last publish committed and is empty before the first (D2; "The published models are selectable"). Failing test: "getModels is empty before the first refresh and serves what publish committed", driving the real provider object through `refreshOmlxCatalog`. This task introduces `createOmlxProvider` with its `refreshModels` wiring; it is not registered until 4.4. Boundary case: a failed refresh leaves the previous list in place, asserted here from `getModels`'s side, and every model it serves carries `provider` `omlx` (2.4's shape, asserted from the list's side).
- [x] 4.2 The hooks pi calls answer in pi's own shapes: `resolve` returns `{auth: {apiKey, baseUrl}, env: {OMLX_BASE_URL}, source}` for a stored credential, and `check` returns `{type: "api_key", source}` without writing a trace line (D3, D11, D14; "A stored credential outranks both environment variables", "A stored credential reports stored"). Failing test: "resolve returns auth, env.OMLX_BASE_URL and source for a stored credential, and check answers configured without a trace line", driving `provider.auth.apiKey.{check, resolve}` with `{ctx: {env, fileExists}, credential, signal}`. Boundary cases: `credential` undefined with no environment key — both answer `undefined`; `check` under `PI_OMLX_DEBUG` writes nothing, which is what keeps the trace in `resolve` alone.
- [x] 4.3 `stream` and `streamSimple` both reach the server, pass `options` through so `before_provider_request` still fires, and the request carries the resolved key — the placeholder for a keyless login (D1; "Chat carries the same placeholder", "A keyed login sends its own key"; `research-chidi.md` Q6). Failing test: "stream and streamSimple reach the fake server, call options.onPayload and carry the resolved bearer". Boundary case: a keyed login sends its own key, not the placeholder.
- [x] 4.4 The factory registers one complete native provider — `id` `omlx`, `auth.apiKey` with `login`, `check`, `resolve`, no `auth.oauth`, and `getModels`, `stream`, `streamSimple`, `refreshModels` — and the legacy registration path is gone (D1, D12; "`/login omlx` reaches the extension's login", "The provider is offered as an API-key login", "No account login is offered" — all three follow from `auth.apiKey` being present and `auth.oauth` absent). `refreshModels` on that same object is what pi's own triggers need; the triggers themselves are Joel's 7.3, since pi is not in the test. Failing test: "the factory registers a native provider with an API-key login and no OAuth handler". Boundary case: `getModels()` is `[]` at registration. This task deletes `toProviderConfig`, `buildOmlxOauth`, `getOmlxApiKey`, `refreshOmlxToken`, `registerLoginOnlyProvider`, the unregister-then-register dance and `state.lastError`, with their tests — and it deletes the fake's `registerProvider(name: string, config)` overload with them, so the fake throws when handed a string and every helper that registered by name drives the Provider object instead (D14: a fake accepting both forms would be forgiving in exactly the place this change is riskiest). Verified by `rg -n "registerProvider: \(provider: string" test` reporting nothing.
- [x] 4.5 The extension makes no catalog request on a timer: advancing the old poll interval and backoff produces no fetch, and no cache file is written anywhere (D12; "No timer refreshes the catalog", "no `cache/omlx-models.json` is written"). Failing test: "advancing the clock performs no catalog fetch and no cache write". This task deletes `startPolling`, `POLL_INTERVAL_MS`, `BACKOFF_BASE_MS`, `refreshProvider`, `fetchAndRegister`, `registerModels`, `registerCachedOrSetupModels`, the cache read, write and path helper with their tests, the `State` fields that only served them, and the `session_shutdown` handler that stopped the poll. Verified also by `rg -n 'omlx-models.json|readCatalogCache|writeCatalogCache|POLL_INTERVAL_MS' src test` reporting nothing, and by `test/index.test.ts`'s "a second load in one process registers again with no shutdown first" staying green — which is what shows the removal needed no shutdown hook (`openspec/specs/test-isolation/spec.md`).
- [x] 4.6 *(guard)* A catalog that lands after the session started moves no model: the extension calls no `setModel` and does not re-run pi's selection (D8; "The extension makes no `setModel` call", "A catalog arriving after startup moves no model"). The test "a late publish leaves the session's model alone" is green from the start, because HEAD makes no `setModel` call (`rg -n 'setModel' index.ts src` finds none): it is a regression guard, not a red-then-green. To show it catching the mistake, Derek inserts one `setModel` call in the publish path, watches the test fail, and reverts it.

## 5. The startup notice

Lands `catalog-discovery`: "A Session Start Warns At Most Once About The Model It Landed On"; `credential-resolution`: "A Saved Login Of The Old Shape Is Not Configured". Designs D8, D9, D13.

- [x] 5.1 A configured start with no `omlx` model shows one warning that names `/model`, and that start shows no second warning (D8; "A configured start with no models warns once"). Failing test: "a configured start with no models warns once and names /model". This task introduces `startupNotice` and the `session_start` wiring. Boundary case: no stored entry at all while an environment-only configuration is in place — the warning still fires, because the predicate goes through `getProviderAuth`.
- [x] 5.2 An OAuth-shaped stored entry takes the warning: the message names `/logout` then `/login`, the landed-model warning is not shown, and the entry's bytes are unchanged (D8, D9; "The OAuth-shaped entry takes the warning", "An OAuth-shaped entry leaves the provider unconfigured", "The extension writes no replacement entry", "The message names the remedy"). Failing test: "an oauth-shaped entry shows the remedy and nothing else". Boundary case: an OAuth entry with models present — the entry still wins.
- [x] 5.3 A configured start with models, and an unconfigured start, show nothing (D8; "A configured start with models warns about nothing", "An unconfigured start warns about nothing"). Failing test: "a warm start and an unconfigured start notify nothing", asserting `ui.notify` was never called.
- [x] 5.4 The configured state comes from `getProviderAuth`, a rejection counts as unconfigured, and the model count comes from `provider.getModels()` (D8; "The configured state comes from pi's provider auth status", "The model count is the list pi chose from"). Failing test: "the notice reads getProviderAuth and provider.getModels". This is the task that catches the predicate mistake: the fake answers `getProviderAuthStatus` with `{configured: true}` while `getProviderAuth` resolves to `undefined`, so a handler reading the status would warn where this test expects silence. Boundary case: `getProviderAuth` rejects — treated as unconfigured, with no error surfacing.
- [x] 5.5 *(guard)* In print and json modes the warning writes nothing (D8; "A run with no session UI writes nothing"). The test "a print-mode start and a json-mode start write nothing to stdout or stderr" is green from the start, because the handler itself writes nothing and the silence comes from pi's `notify` being a no-op: it is a regression guard, not a red-then-green. To show it catching the mistake, Derek adds a `console.warn` beside the handler's `notify` call, watches the test fail, and reverts it.
- [x] 5.6 *(structure)* `catalogNotice` and its three message helpers are deleted from `src/notice.ts`, and the old notice tests with them; the module is `startupNotice` alone (D8, D12). Verified by `npm run check` green and `rg -n 'catalogNotice|unavailableWithCache|unavailableLoginOnly|arrivedLoginOnly' src test` reporting nothing.
