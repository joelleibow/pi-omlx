## 1. Decisions that bind this change

- **Joel, `owner-rulings.md` §1 (2026-11-11):** "Tests never mutate operating functionality." Decided: the suite must not write to, or read from, the operator's real pi agent directory, *whatever environment it is run in*. Consequence I draw from "whatever environment": the isolation must assign unconditionally and override a caller's own `PI_CODING_AGENT_DIR` (Chidi F2: `??=` does not override; unconditional assignment does). A contributor cannot point the suite at a directory of their choosing. That is the ruling, not a design option.
- **Joel, `owner-rulings.md` §2:** test-only seams are a smell; removing them is its own card; this change adds no production code that exists only for tests. `_setAuthPathForTesting` (`src/auth-storage.ts:19`) and its call sites (`test/index.test.ts:37,42`, `test/auth-storage.test.ts:18,21`) stay.
- **Joel, `owner-rulings.md` §3:** this card runs now.
- **Joel, archived `make-check-pass-on-pi-1-5-2/owner-rulings.md` §3 and `one-credential.../owner-rulings.md`:** "Until the board card that isolates the tests lands, every run of the suite ... sets `PI_CODING_AGENT_DIR` to a scratch directory." This card is that card; it retires the condition, it does not inherit it.
- **My prior rulings (archived `one-credential.../council.md` lines 22, 42):** wiring tests take the `PI_CODING_AGENT_DIR` route (pi reads `getAgentDir()` per call, `config.js:510-516`, re-checked); seam call sites stay for the seam card; `readLastCatalogCache` deferred. Those bind here.
- **Living requirement this change modifies:** `openspec/specs/verification/spec.md` Requirement 3 "Verification Runs Leave The Operator's Agent Directory Alone" (lines 32-40). Its premise sentence "until it isolates itself, the variable is the isolation" and its WHEN clause (`PI_CODING_AGENT_DIR=<scratch directory> npm run check`) are exactly what this change makes false. Requirement 1's scenario WHEN clause (line 14) carries the same prefix and goes with it. The scenario's live citation `test/index.test.ts:72,76` is a line-number pointer the test file holds steady with a comment (`index.test.ts:100-101`); the rewrite should cite the fixture by name, not by line.
- **Standing records, not decisions:** `AGENTS.md:23` trap and `CONTRIBUTING.md:14` (docs; Bambadjan's pass after the gate, never blocking). `ARCHITECTURE.md` §4/§9 and ADR 0001: the extension reads `auth.json` and never writes it — a test fixture writing `auth.json` is test setup, not the extension, and stays legitimate.
- **Chidi's report** is evidence. Its correction stands: `poolOptions` is gone in vitest 5.1.0 (`npm ls` → 5.1.0 confirmed); `pool`/`isolate`/`execArgv` are top-level; default pool `forks`, `isolate: true`, and `vitest.config.ts` sets none of them.

## 2. Traps, measured

**a. Module-load-time path (the defect behind finding 2).** `src/catalog.ts:567` `const CACHE_FILE = join(getAgentDir(), "cache", "omlx-models.json")` is computed at import; `:598` `mkdirSync(join(getAgentDir(), "cache"))` is computed per call. Two derivations of one fact, and they disagree at runtime. Measured in the scratch copy (`.pi/marbleization/.../scratch`, `HOME` = empty dir, `PI_CODING_AGENT_DIR` unset): running only `test/index.test.ts -t "stored credential decides"` — a test that sets `PI_CODING_AGENT_DIR=dir` via `withEnv` (`index.test.ts:222`) — wrote `$HOME/.pi/agent/cache/omlx-models.json` with the fixture `apiRoot https://omlx.home.g33k.top/v1`. The per-test env isolates the `auth.json` read (per call) and the `mkdir`, not the cache write. The comment at `index.test.ts:104-107` claiming the test's dir is where production resolves is true for the read and false for the write. Whatever mechanism is chosen, the variable must be in `process.env` before `src/catalog.ts` is first imported in each worker (Chidi F8: `test.env`, `globalSetup` assigning `process.env`, or an unconditional `setupFiles` assignment qualify; `vi.stubEnv` after imports and `provide/inject` alone do not).

**b. Full bare run, measured.** `env -u PI_CODING_AGENT_DIR HOME=<empty> npx vitest run` in the scratch copy: 88/88 green, and `HOME` afterwards holds `.pi/agent/cache/omlx-models.json` (fixture content), plus `.npm/_logs/*` and `.npm/_update-notifier-last-checked` (npx's), and `Library/Application Support/vitest/.vitest-secret-token` (vitest's own). The rewritten scenario must assert on `.pi` and `.omlx` under `HOME`, not "nothing under HOME", or npm and vitest fail it.

**c. The operator's `~/.omlx` overlay reaches the suite's outcome.** `src/catalog.ts:610` `join(homedir(), ".omlx", "model_settings.json")`; `index.ts:261` passes it to `fetchModels` → `applyLocalModelSettings`. `PI_CODING_AGENT_DIR` cannot touch this. Measured: with `HOME/.omlx/model_settings.json` = `{"models":{"real-model":{"max_tokens":0}}}`, **10 of 16 `index.test.ts` tests fail** (`isRegistrableModel` rejects the fixture model). Joel's real `~/.omlx/model_settings.json` exists (7467 B); today the suite passes only because it has no `real-model` entry. Only overriding `HOME` (or `OMLX_MODEL_SETTINGS_PATH`) isolates this.

**d. The `.env` loader.** `index.ts:10` `loadDotenvFromExtensionDir(import.meta.url)` runs at import and merges `<repo>/.env` into `process.env` for keys that are unset or empty (`src/dotenv.ts:32`). `withEnv` clears four keys (`index.test.ts:118-123`) but not `OMLX_MODEL_SETTINGS_PATH`; the first test (`index.test.ts:46`) uses no `withEnv` at all. Measured: a scratch `.env` with `OMLX_MODEL_SETTINGS_PATH=<poisoned overlay>` → **4 failures**. `.env` is gitignored and `.env.example` invites creating it. Isolation must set `OMLX_MODEL_SETTINGS_PATH` (and clear `OMLX_BASE_URL`/`OMLX_API_KEY`) before `index.ts` loads; because `mergeDotenv` only fills unset keys, an assigned value wins over `.env` for free.

**e. `HOME` under worker modes.** `os.homedir()` honours `$HOME` only if set before the process starts (Chidi F12, re-derived): under the default `forks` pool a `HOME` set in `globalSetup` or `test.env` reaches `homedir()`; under `threads`/`vmThreads` it changes `process.env.HOME` but not `homedir()`. The repo is on forks today; a future `pool: "threads"` silently un-isolates `~/.omlx`. The guard in (g) is what catches that.

**f. Cleanup.** `test/catalog.test.ts:233,311,467` `mkdtempSync` with no `rmSync`: three leaked dirs per run; the machine's tmpdir holds **443** `pi-omlx-*` dirs now. `index.test.ts` and `auth-storage.test.ts` do remove theirs. The mandated `.pi/marbleization/.../agent-dir/cache/omlx-models.json` persists across runs, so today's suite already runs against a cache file the previous run wrote (`registerCachedOrSetupModels` reads it keyed by the fixture `apiRoot`); it happens to assert nothing that depends on it (green with and without a pre-existing cache). A per-run `mkdtemp` isolation root removed at teardown starts every run clean and, if tests mkdtemp under it, sweeps the leak too. Chidi F9b: `globalSetup` teardown runs on normal exit and after failing tests but not on SIGINT/SIGTERM; a `process.once("exit", rmSync)` registered in setup does run on those (SIGKILL excepted).

**g. A guard that proves nothing escapes.** Two layers, neither adds production code. (i) Outside the suite, Requirement 3's scenario becomes the measurement in (b): run bare with `HOME` pointed at an empty directory; afterwards `HOME/.pi` and `HOME/.omlx` do not exist. (ii) Inside the suite, a `setupFiles` assertion (Chidi F13) that `getAgentDir()` and `os.homedir()` both resolve under the isolation root and that `process.env.OMLX_MODEL_SETTINGS_PATH` points under it — it throws before any file collects, and it fails if someone switches to the threads pool (e) or removes the config. Show it catching a mistake by running it once with the pool set to threads or the env line removed. Node's permission model (Chidi F14) is a third layer I would not add: `--allow-child-process`/`--allow-worker` with Node warnings and an untested pi load path, for a property (ii) already proves. Deletion test: nothing breaks without it.

**h. Boundary with the seam-removal card.** This change must leave `_setAuthPathForTesting` and its call sites alone, and must make the seam card safe: once `_setAuthPathForTesting` goes, `index.test.ts:46` (no `withEnv`) reads `auth.json` from `getAgentDir()`, which in a bare run is the real `~/.pi/agent/auth.json` unless the run-wide isolation is in place. Per-test `auth.json` under a per-test `PI_CODING_AGENT_DIR` already works (pi reads per call, `auth-storage.js:425`). The cache write does not follow a per-test dir (trap a) until `CACHE_FILE` is derived per call; that one-line correction (`cacheFile()` replacing the constant, and `:598` reading the same derivation) is production code with a production reason — one fact, one place — not a test-only seam, so ruling §2 does not forbid it. I would include it: it is what lets the seam card say "the agent directory variable is the replacement" (`ARCHITECTURE.md` §9) truthfully. Also out of this card: `readLastCatalogCache` (deferred, `AGENTS.md` trap).

**i. Provenance of the mechanism.** Chidi F3: `globalSetup` → `process.env` → worker inheritance is source-derived (`index.Di8au7q4.js` ~L6116 spread order) and experimentally confirmed in all pools, but the vitest docs promise only `provide`/`inject`. `test.env` is documented, but a `mkdtemp` in `vitest.config.ts` has no teardown hook of its own (F9d) — though `globalSetup`'s teardown can read `project.config.env.PI_CODING_AGENT_DIR` and remove it, which is documented on both ends. Either route is acceptable to me provided the in-suite guard (g.ii) exists, because the guard turns the undocumented claim into a measured one every run. The design must say which it leans on and cite F1/F3.

**j. Unconditional override.** `withEnv` (`index.test.ts:129`) deletes `PI_CODING_AGENT_DIR` then reassigns; `restoreEnv` puts the run-wide value back. `auth-storage.test.ts:17-23` saves and restores. Both keep working under a run-wide value; neither needs rewriting for this card.

## 3. Calls that are certainly Joel's

1. **Scope of "operator state".** Ruling §1 names the pi agent directory. The two other reads the suite makes of the operator's machine — `~/.omlx/model_settings.json` (trap c, 10 failures measured) and the repo `.env` (trap d, 4 failures) — are outside its letter and inside its reason. Cost of including: a `HOME` override and one more env key, both set in the same place as `PI_CODING_AGENT_DIR`; no new mechanism. Cost of excluding: the suite stays non-deterministic on any machine with an overlay entry for `real-model`, and the next time it fails that way someone writes a new card. My recommendation: include both; I would write the design that way and ask him to confirm rather than block on him.

Nothing else here is his. Where the isolation root lives, which vitest mechanism carries it, whether `CACHE_FILE` becomes per call, and whether the `PI_CODING_AGENT_DIR=` prefix leaves the spec's WHEN clauses and the docs are mechanism or documentation, and I have said what I would choose: a per-run `mkdtemp` root under `os.tmpdir()`, assigned unconditionally before any test file imports, removed at teardown and on `exit`; `CACHE_FILE` derived per call; the prefix dropped everywhere, because keeping it says we do not trust the isolation this card exists to build.

## 4. The strongest challenge

The honest challenge is that a run-wide `HOME`/`PI_CODING_AGENT_DIR` override in vitest configuration is ceremony around one production defect: `CACHE_FILE` is computed at import while every other agent-directory path in the extension and in pi is computed per call. Fix that line, and every existing test that touches the agent directory already sets `PI_CODING_AGENT_DIR` per test with a temp dir it removes — the suite isolates itself by its tests' own discipline, with no config, no global setup, no undocumented env inheritance, and no coupling to the forks pool. It is the smaller diff and it leaves vitest alone. It fails Joel's ruling on two measured points: `index.test.ts:46` sets no env and would still write the real cache on the first test, and `~/.omlx/model_settings.json` is reached through `homedir()` by every wiring test regardless of the agent-directory variable (10 failures with a poisoned overlay). Discipline is not a guard, and "whatever environment it is run in" asks for a guard. So the per-call fix is part of the answer, not the answer; the run-wide override plus the setup-file assertion is what turns the ruling into something the suite proves on every run.
