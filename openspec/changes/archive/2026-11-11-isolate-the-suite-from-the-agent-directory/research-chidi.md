# Research Report

## Question and Scope

How a vitest suite can isolate an extension (pi-omlx) from the operator's real pi state, so `npm run check` neither reads nor writes `~/.pi/agent`. Binding ruling (`owner-rulings.md`, 2026-11-11): "Tests never mutate operating functionality"; the suite must not write to or read from the real agent directory "whatever environment it is run in". A second ruling forbids production code that exists only for tests. This report is evidence only; it makes no design recommendation.

Five questions: (1) every vitest mechanism that can set env / create a temp dir before test modules import; (2) which of them guarantee a module-load-time constant like `CACHE_FILE` sees the variable; (3) cleanup and teardown guarantees; (4) what else pi 1.5.2 derives from `HOME` / the agent dir, and whether `PI_CODING_AGENT_DIR` alone isolates it; (5) guards against touching the real home.

Versions: vitest **5.1.0** (`node_modules/vitest/package.json`), Node v26.8.1, macOS, pi-coding-agent **1.5.2**. Repo config `vitest.config.ts`: `environment: node`, no `pool`/`isolate`/`env`/`setupFiles`/`globalSetup` set, so defaults apply (pool `forks`, isolate true).

Method tags: **[src]** = read in installed vitest/pi source; **[doc]** = vitest.dev (the installed package ships no prose docs, only `.d.ts` and minified-ish dist, so online docs were used for prose/semantics); **[exp]** = my own experiment in a scratch project `/tmp/vt` (symlinked to this repo's `node_modules`, vitest 5.1.0, nothing in the repo modified).

## Findings

### Q1. Mechanisms, timing, reach

**F1 — `test.env`.** Applied in two places [src]: (a) when the pool builds each project's worker env: `env = { ...process.env, ...options.env, ...ctx.config.env, ...project.config.env }` (`index.Di8au7q4.js` ~L6116-6121), passed as `env:` to `child_process.fork` (L5491) or `new Worker` (L5597); (b) in-worker `setupEnv(config.env, metaEnv)` (`base.Cof-UHJf.js` L176), where `metaEnv` is a Proxy over `process.env` (`init.CO4AB7HZ.js` L204-225), run in `setupBaseEnvironment` before any setup file or test file is imported. Doc [doc]: "Environment variables available on `process.env` and `import.meta.env` during tests. These variables will not be available in the main process (in `globalSetup`, for example)." Consequences: it is static config (a literal or something computed when the config file loads); it wins over the caller's ambient env (spread order, and [exp] below); it applies once per worker, every file. Works under forks, threads, vmThreads, vmForks and `--no-isolate` [exp, all 3 files saw the value in every combination]. Limitation [exp]: under `threads`/`vmThreads`, a `HOME` set this way changes `process.env.HOME` but **not** `os.homedir()` (see F9).

**F2 — `setupFiles`.** Run **before each test file, in the same process as the tests** [doc, src `collectTests` L3456-3460: `runSetupFiles` then `importFile(filepath)`]. Order between setup files is sequential by default (`sequence.setupFiles`). Runs per file, not per run. With `isolate: false` the worker and module cache are reused but the setup file body "is executed again before each test file" [doc]. Works in forks/threads/vm pools and `--no-isolate` [exp]. A setup file can set `process.env.X` or create a temp dir, but a per-file creation yields one dir per file unless it is guarded. Note [exp]: `process.env.X ??= ...` does not override a caller-supplied value; unconditional assignment does.

**F3 — `globalSetup`.** Runs **once per run in the main process** before workers are created, "only if there is at least one test queued" [doc]; src: `initializeGlobalSetup(specs)` is awaited before `pool.runTests` (`cli-api.COfZo8lK.js` L13413). Receives a `TestProject`; may return a teardown function or export `teardown`. Setup/teardown are sequential, teardown in reverse order [doc]. **Environment reaches workers via `process.env`**: because the worker env is built at `runTests` time from `...process.env` (F1 src), a `process.env.X = ...` assignment in `setup()` is inherited by every worker. [exp] confirmed for forks, threads, vmThreads, vmForks, and with `--no-isolate`: every file's worker saw the value, including at module-import time. This is source/experiment-derived; the globalSetup doc page does not itself promise env inheritance — it documents `provide`/`inject` as the supported channel. Also [exp]: assignment here overrides a caller-supplied value of the same variable (it precedes the spread; `config.env` still overrides it if both set). `os.homedir()` for `HOME` set this way is correct in all pools [exp] because it mutates the real process env that threads inherit at startup.

**F4 — `provide`/`inject`.** `project.provide(key, value)` (serialisable only; throws "Cannot provide … not serializable", `index.Di8au7q4.js` ~L6525) in `globalSetup`, read with `inject(key)` in tests/setup files [doc /config/globalsetup]. It is a channel for *values*, available inside a test or setup file at run time; it does not set `process.env`. It is therefore not usable by a module that reads `process.env` at import unless a setup file first copies it to `process.env`. (Whether `inject` is callable at the top of a setup file before other imports: not tested.)

**F5 — `poolOptions`.** Not a mechanism in 5.1.0: `test.poolOptions` "was removed in Vitest 4. All previous `poolOptions` are now top-level options" (deprecation message, `index.Di8au7q4.js` L8823). Relevant top-level successors: `pool` (default `forks` [doc /config/pool]), `isolate` (default `true`, no effect on vm pools [doc /config/isolate]), `execArgv` (extra Node args for the worker [doc /config/execargv]). I did not look up per-pool env options; none exist for env in 5.1.0 config types that I found.

**F6 — `vi.stubEnv`.** Runs in the test/setup/file context, after workers start. [exp] A top-level `vi.stubEnv("PROBE", …)` in a test file placed *after* a static `import` of the module is **too late** for that module's import-time constant (const read `UNSET`, runtime value `late`). `vi.hoisted(() => vi.stubEnv(...))` runs before the file's imports and the constant saw it. It is per file. With `test.unstubEnvs: true` (default `false`) env is restored before each test, which unsets the value for later tests while module-load constants already computed stay computed [exp]. A stub in a `setupFiles` entry is also per file.

**F7 — Execution order, one worker, [src+exp].** main: config load → `globalSetup.setup()` → pool builds worker env from `process.env`+`config.env` → worker: `setupEnv(config.env)` → `setupFiles` → import test file (and its static imports) → tests.

### Q2. Import-time constants (`CACHE_FILE`)

**F8.** A value must be present in `process.env` before the test file's import graph executes. Guaranteeing this in every worker for every file: **`test.env`** (F1, both at fork/thread creation and in `setupBaseEnvironment`), **`globalSetup` setting `process.env`** (F3), and **a `setupFiles` entry that sets it unconditionally** (F2; runs before each file's import) all qualified in every pool and in `--no-isolate` [exp, a `const.ts` module doing `const C = process.env.PROBE` imported by 3 test files, 3 files × 4 pools × isolate on/off]. Not sufficient: `vi.stubEnv` after imports (F6), `provide`/`inject` alone (F4). With `--no-isolate`, the import-time module cache is shared across files in a worker, so the constant is computed once per worker from the env at that moment; since all three mechanisms set the same value for all files that is not observably different [exp]. A mixture, such as `test.env` fixed path plus a different per-file dir, would not be coherent with a once-computed constant under `--no-isolate` (reasoning, not run).
Also noted: a module that is imported by `globalSetup` itself or by `vitest.config.ts` runs in the main process with the main process's env, not the worker's.

### Q3. Cleanup

**F9a — globalSetup teardown.** Returned function (or exported `teardown`) is called "after all test files have finished running"; in watch mode, before the process exits [doc]. Src: `Vitest.close()` runs `_teardownGlobalSetup()` for every project in reverse before closing the pool (`cli-api.COfZo8lK.js` L13778), and teardown errors are collected and logged ("error during close"), not thrown. [exp]: teardown ran after a run with a failing test (exit code non-zero, dir removed).

**F9b — signals.** [exp] On `SIGINT`, `SIGTERM` (sent to the main vitest process while a test was running), the globalSetup teardown did **not** run and the temp dir was left behind. Source explains: `addCleanupListeners` (`index.Di8au7q4.js` L8598-8610) registers `once('SIGINT'|'SIGTERM'|'exit')` that only clears the terminal then `setTimeout(() => process.exit(), 1)`; exit code 130/143 observed. A synchronous `process.once("exit", () => rmSync(dir, …))` registered inside `setup()` **did** remove the dir on SIGINT and SIGTERM [exp] (the vitest handler calls `process.exit()`, which fires `exit`). On `SIGKILL` nothing runs; the dir remained [exp] (unavoidable in general). Console-shortcut handling (`registerConsoleShortcuts`, `ctx.exit(true)` after `cancelCurrentRun`) applies in interactive/watch mode; not tested.

**F9c — setupFiles cleanup.** `afterAll` registered in a setup file is a hook per test file (the setup file is re-run per file; hooks reset per file [doc /config/setupfiles example]). So it removes at the end of each file, not the end of the run; unsuitable for one shared dir. Workers run in other processes/threads than the main process, so main-process `exit` handlers don't cover worker-created dirs.

**F9d — config-file creation.** A dir created at top level of `vitest.config.ts` has no teardown hook of its own. Not tested; I note only that config is loaded by the main process per invocation.

**F9e — failed setup.** [exp] A `setup()` that throws surfaced as a stack trace in the output; I observed shell exit 0 in my pipeline but that is the exit of `tail`, so the vitest exit code on global setup failure was **not** verified.

### Q4. pi 1.5.2

**F10 — `getAgentDir()` / `CONFIG_DIR_NAME`** (`config.js`): `CONFIG_DIR_NAME = pkg.piConfig?.configDir || ".pi"` (L492); `ENV_AGENT_DIR = "PI_CODING_AGENT_DIR"` (APP_NAME.toUpperCase()+`_CODING_AGENT_DIR`, L495); `getAgentDir()` (L510-516) returns `expandTildePath(process.env.PI_CODING_AGENT_DIR)` if set and non-empty (an empty string falls through), else `join(homedir(), CONFIG_DIR_NAME, "agent")`. It is read **per call**, not cached. `getAgentDir`, `CONFIG_DIR_NAME`, `readStoredCredential` are exported from `index.js` (L4-6). Pi's own helpers all derive from it: `models.json`, `auth.json`, `settings.json`, `tools/`, `bin/`, `prompts/`, `sessions/`, `themes/`, `${APP_NAME}-debug.log` (`config.js` L518-551); also `models-store.json` (`core/models-store.js` L30), `crashes.json` (`core/crash-log.js` L7), keybindings, the project-trust store (`new ProjectTrustStore(agentDir)`), extension/skill discovery default `agentDir = getAgentDir()`.

**F11 — what `PI_CODING_AGENT_DIR` alone does not isolate.** (a) `homedir()`-based paths: `~/.agents/skills` user skills (`package-manager.js` L2182 via `getHomeDir()` = `process.env.HOME || homedir()`, L84; `trust-manager.js` L158-159 same), tilde expansion in `utils/paths.js` `normalizePath` (L112, `homedir()`), `~/.cache/huggingface/token` (`extensions/llama/huggingface.js` L34), `~/.bun/install/global` (`config.js` L167, L192), MCP paths (`extensions/mcp/runtime.js` L47-49). (b) the session dir has its own override `PI_CODING_AGENT_SESSION_DIR` (`config.js` L496; `main.js` L599) and a `sessionDir` setting; default is under the agent dir. (c) project-scoped `cwd/.pi` and `.agents` are relative to cwd, not home. (d) The extension under test itself uses `homedir()` independently: `src/catalog.ts` L610 `join(homedir(), ".omlx", "model_settings.json")`; this read is not governed by `PI_CODING_AGENT_DIR` at all. Whether pi-omlx's tests exercise a path that reaches (a) through pi was not traced; the extension only imports `getAgentDir` and `readStoredCredential` from pi per `src/*.ts` greps.

**F12 — `HOME` effect.** `os.homedir()` on POSIX honours `$HOME` [exp: `HOME=/x node -e 'console.log(os.homedir())'` → `/x`]. But under `pool=threads` / `vmThreads`, setting `HOME` via `test.env` or in a setup file changes `process.env.HOME` inside the worker but `os.homedir()` still returns the real home [exp, 3 mechanisms × 3 pools]; only a main-process change before workers spawn (globalSetup / config file) or a forks/vmForks pool gave a correct `homedir()` in every case [exp]. Pool default is `forks` [doc], and the repo config sets none.

### Q5. Guards

**F13 — vitest.** I found no vitest option that fails a run when a test resolves or touches a path under the real home: no config key in the 5.1.0 `config.d.ts` for fs sandboxing for node-environment tests, and none in the doc pages read. Vite's `server.fs.allow` concerns the dev server, not test fs calls (not verified against docs; I did not read it). Convention-level guard available in the existing mechanisms: a `setupFiles` (or `globalSetup`) assertion that `process.env.PI_CODING_AGENT_DIR` (and `HOME` if overridden) is set and under `os.tmpdir()`, throwing before tests collect (a throwing setup file fails that file's collection: `collectTests` catches and records the file as failed, `run.CjdgFZiW.js` L3470-3480). I did not find a published community convention in the sources read; treat "assert in a setup file" as an obvious use of F2, not a cited convention.

**F14 — Node permission model via `execArgv` (not a vitest feature, works through F5's top-level option).** [exp] `test: { execArgv: ['--permission','--allow-fs-read=*','--allow-fs-write=<scratch>','--allow-child-process','--allow-worker'] }` with `pool=forks`: tests ran and a `mkdirSync` under `/Users/joelleibow/` failed with `ERR_ACCESS_DENIED` while allowed paths worked; Node emitted `PERM0002`/`PERM0006` security warnings for the two `--allow-*` flags. Costs/unknowns: worker flags apply per worker, so the allowed write path must be known at config load; whether pi / other dependencies load under the permission model for the full suite was not tested; `--allow-child-process`/`--allow-worker` weaken it (Node warns). Under `threads` pool not tested.

## Assumptions, Differences, and Unknowns

- Brief's assumption "`poolOptions`" as a mechanism: in vitest 5.1.0 it is removed (deprecation at L8823); top-level `execArgv`/`pool`/`isolate` replace it. It never carried `env`.
- Brief's assumption that `PI_CODING_AGENT_DIR` isolates "all of it": it isolates everything pi routes through `getAgentDir()`, but not `HOME`-derived paths (F11) or the extension's own `~/.omlx` read.
- The brief's phrase "isolate: whether it works under `--no-isolate`": all three env mechanisms did; the caveat is only that setup files re-run per file and module constants are computed once per worker.
- Not verified: globalSetup failure exit code; behaviour in watch mode and with `vitest --ui`/interactive Ctrl-C; per-project (`projects`/workspace) inheritance of `globalSetup` (`index.Di8au7q4.js` L3711 shows root globalSetup is not inherited by non-root projects — relevant only if the repo adopts projects); the full pi-omlx suite under the Node permission model; `inject()` availability at the top of a setup file; vitest's online `/guide/migration` page (cited via the installed deprecation message instead).
- vitest.dev is the live site (latest); it may differ from 5.1.0 in unread details. The installed source was cross-checked for the points relied on (env spread order, global setup ordering, teardown order, setup-file execution).
- All experiments ran in `/tmp/vt`; nothing in the repo was modified except this file. Scratch dir left in `/tmp/vt`.

## Addendum 1 — mocks from a setup file

Measured in `.pi/marbleization/isolate-the-suite-from-the-agent-directory/scratch` (copy of repo; vitest 5.1.0; `PI_CODING_AGENT_DIR`=a `mktemp -d`; default pool forks; probes in `scratch/probe/`, one config per setup file, `--no-isolate` repeated). Repo untouched.

**(1) `vi.mock` of a module `index.ts` imports: yes, both modes.**
Setup `su-mock-src.ts`: `vi.mock("../src/provider.ts", () => ({ toProviderConfig: () => "MOCKED" }))`. Test `p1` imports `../index.ts` and also imports `toProviderConfig` from `../src/provider.ts` directly.
Output (default and `--no-isolate`): `direct provider.toProviderConfig typeof result=MOCKED`. The test's own direct import was mocked, which shows the registry is shared; `index.ts` imports the same specifier/resolved id, so it gets the mock. I did not separately assert on `index.ts`'s internal binding.

**(2) `node:fs` mocks affecting `src/dotenv.ts` (via `index.ts`):**
- `vi.mock("node:fs", async (orig) => ({ ...await orig(), default: a, existsSync: p => { log(p); return false } }))` in setup: **yes**, both modes. `dotenv.ts`'s `existsSync` was called with `<scratch>/.env` and logged: `fsmock calls=[".../scratch/.env"]`.
- `vi.spyOn(fs, "existsSync")` with `import fs from "node:fs"` in setup: **no effect**, both modes: `spy calls=[]` (spy installed on the default-export object; `dotenv.ts` uses the named ESM binding).
- `vi.spyOn(ns, "existsSync")` with `import * as fs`: **throws**: `Cannot spy on export "existsSync". Module namespace is not configurable in ESM.`

Caveats: mocks and `restoreMocks`/`clearMocks` config were not combined with the repo's own config (probe configs omit `restoreMocks: true`); a `vi.mock` factory is not reset by `restoreMocks`, but I did not test that. `scratch/probe/out.txt` and configs remain in scratch. `PI_CODING_AGENT_DIR` stayed empty after runs.
