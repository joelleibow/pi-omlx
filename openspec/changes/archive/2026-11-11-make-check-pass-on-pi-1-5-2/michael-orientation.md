== 2. Traps, measured ==

Baseline I re-derived: `npx tsc --noEmit` at HEAD = 10 errors (provider.ts:35,37 + test/provider.test.ts:49-53,60,66,72); `npm ls` shows top-level pi-ai 0.80.10 and nested 1.5.2 under pi-coding-agent and pi-agent-core. Eleanor's scratch (devDep ^1.5.2) dedupes to one 1.5.2 and shows exactly 9 errors (stream.ts:126,209 TS2741 + the 8 test errors). Both reports' load-bearing claims check out.

(a) Dev copy ≠ the copy pi loads. Confirmed from source: pi's loader aliases root and `/compat` to its own extension view (Chidi §1.2; `openAICompletionsApi` is on compat only — `compat.js:19,36`, absent from root index). So production never executes the repo's node_modules pi-ai; tsc is the only consumer of the devDep. The check is therefore green iff devDep pi-ai == pi-coding-agent's pinned pi-ai. After the bump both are ^1.5.2 and the lockfile holds them together, but nothing structural ties them: 429742d bumped one caret alone and produced this bug, and `.github/dependabot.yml` has no `groups`, so dependabot will open per-package PRs that recreate the split. Mitigation: tsc itself is the detector (the split surfaces as the two provider.ts errors), so I would NOT add mechanism; see Joel's call #1.

(b) Casts/suppressions standing in for fixes. Baseline has zero `@ts-ignore/@ts-expect-error/biome-ignore`; four `as unknown as` casts in tests (stream.test.ts:93, oauth-login.test.ts:92, provider.test.ts:94, index.test.ts:61) and two `model as Model<"openai-completions">` in production (stream.ts:125,208, same shape as pi's gitlab-duo example :331-341). All pre-existing. The trap for THIS change: provider.test.ts:94 already dodges the ProviderModelConfig union with `as unknown as Record<string,unknown>`; copying that onto :49-72 would be a cast in place of a fix. `ProviderChatModelConfig` is NOT exported from pi-coding-agent's index (only ProviderConfig, ProviderModelConfig — dist/index.d.ts:8), so a named cast isn't even available; the honest route is a discriminant narrowing (`m.type !== "image" && m.type !== "classifier"`, Chidi §4.3). A bare `m.type === "chat"` would be WRONG: production `toProviderModel` (provider.ts:60-73) omits `type`, which pi normalizes to chat (types.d.ts:1530). I ran this: a 4-line `chat(m)` helper in the test that throws on image/classifier and returns the narrowed member compiles, and a mutation (`thinkingDefault !== false` in provider.ts:61) still fails the test — the helper does not weaken the assertion.

(c) Test fixtures can't produce a real TranscriptContext. Measured: the brand is type-only. `normalizeContext` (pi-ai 1.5.2 `dist/utils/transcript.js:23-27`) returns a plain `{ messages }`; it is exported from root (`index.d.ts:33`). So `normalizeContext({ messages: [] })` in test/stream.test.ts:123 and :293 yields a real TranscriptContext with no cast, and the brand still bites a literal (I got TS2741 when I left `{ messages: [priorAssistant] }` typed as TranscriptContext). No identity assertion on the context exists in the tests (only `captured?.model.provider`, :206), so the fresh wrapper object changes nothing. The mock's `streamSimple` signature may keep `Context` or move to `TranscriptContext`; TranscriptContext is assignable to Context (repeat-stop.ts:61 keeps `Context` untouched). Production change is three type tokens in stream.ts (:5, :91, :185): purely nominal, zero runtime diff — pi already hands the wrapper a TranscriptContext and the wrapper forwards it unchanged.

Yes: npm passes the environment through, so `PI_CODING_AGENT_DIR=<isolated> npm run check` is a literal run of the ruled-on script. == 4. Strongest challenge ==

This change makes tsc agree with pi 1.5.2's types, but what it type-checks against is still the repo's own copy of pi-ai — a copy pi never loads — and nothing in the repository ties that copy's version to the one pi-coding-agent pins. The green check is a coincidence of two independent caret ranges resolving to the same number today; Joel's own commit 429742d is the proof that they drift, and dependabot is configured to drift them one package at a time. Meanwhile the production edit is three type annotations with no runtime effect, so the change buys a green light and no new runtime guarantee. The honest answer is that the green light IS the guarantee Joel asked for: when the copies split, tsc goes red at provider.ts:35,37 and says so, which is "something is wrong and we know what" — the opposite of the state he objected to. The alternative that removes the duplicate by construction (drop the pi-ai devDep and let npm hoist pi-coding-agent's nested 1.5.2) trades an explicit dependency for a phantom one and fails the moment hoisting changes.
