## Findings

### 1. Request auth

Chat path: `sdk.js:261-271` `streamFn` -> `ModelRuntime.streamSimple` (`model-runtime.js:504-529`) -> `prepareRequest` (`:459-492`) -> `getAuth` (`:369`) -> pi-ai `Models.getAuth` (`AI/models.js:348-360`) -> `resolveProviderAuth` (`AI/auth/resolve.js:10-39`).

Order in `resolveProviderAuth`:
0. A per-call `overrides.apiKey` (only if `provider.auth.apiKey` exists) (`resolve.js:17-23`). `prepareRequest` passes `options?.apiKey` here (`model-runtime.js:463-467`). Not a stored/configured source.
1. Read the stored credential (`resolve.js:24`). `RuntimeCredentials.read` returns a runtime api key (`setRuntimeApiKey`) as `{type:"api_key",key}` ahead of auth.json (`runtime-credentials.js:19-22`).
2. Stored **oauth** and `provider.auth.oauth` exists -> `resolveStoredOAuth` (`resolve.js:26-28`, `:100-123`): refresh if <5 min to `expires` (`:101-116`), then `oauth.toAuth(credential)`, source "OAuth".
3. Stored **api_key** and `provider.auth.apiKey` exists -> `resolveApiKey` with that credential (`resolve.js:29-32`).
4. Stored credential of a type with no matching method -> `undefined` (not configured); no env fallback (`resolve.js:33`; doc comment `:5-8`: "A stored credential owns the provider: ambient/env is consulted only when nothing is stored").
5. Nothing stored -> `apiKey.resolve` with `credential: undefined` (`resolve.js:36-38`), i.e. the configured `apiKey` string/env.

So the order is: stored oauth, else stored api_key, else configured `apiKey` string (interpolated from env), else nothing. A stored credential always shadows the env; there is no fall-through after a failed refresh.

`composeApiKeyAuth` (`provider-composer.js:244-311`), resolve at `:284-309`:
- `input.credential` present (stored api_key): no `inherited` (omlx is not a builtin) -> `input.credential.key` truthy gives `{apiKey: key, source:"stored credential"}` (`:286-291`); an empty/missing key gives `undefined` (not configured, no env fallback).
- No credential, `rawKey !== undefined`: `resolveConfigValueOrThrow(rawKey, ...)` interpolates env (`:293-299`), `source:"configured API key"`. An unset env var throws `Failed to resolve API key for provider "omlx" from environment variable: OMLX_API_KEY` (`resolve-config-value.js:199-218`).
- Neither -> `inherited?.resolve` -> `undefined` (`:300-302`).
- `authHeader` (`:252`, `extension.authHeader ?? config.authHeader ?? false`) is applied to the result via `withConfiguredAuth` (`:308`).
- Important gate: `composeApiKeyAuth` returns `undefined` (no api-key method at all) when there is no inherited auth, no `rawKey`, and an `oauth` exists (`:249-250`). In the keyless registration (no `apiKey`, with `oauth`) a stored `api_key` credential therefore hits step 4 and the provider is unconfigured for requests (`resolve.js:29,33`); `resolveRefreshCredential` likewise returns `undefined` (`AI/models.js:258-259`).

`composeOAuthAuth` (`provider-composer.js:312-327`): wraps the `adaptOAuth`-adapted extension oauth (`:196-215`). `adaptOAuth.toAuth` returns **only** `{ apiKey: config.getApiKey(credential) }` (`:213`); `login` returns `{...credential, type:"oauth"}` (`:210`), so extra fields (e.g. `baseUrl`) are stored; `refresh` also keeps returned fields (`:212`). `composeOAuthAuth.toAuth` then runs `withConfiguredAuth(auth, headers, authHeader)` (`:320-325`).

`authHeader` in each case (`withConfiguredAuth`, `provider-composer.js:216-224`):
- false/unset: no Authorization header added by pi; `apiKey` is passed in `options.apiKey` (`model-runtime.js:487`) and the stream implementation decides how to send it (the openai-completions client uses `options.apiKey`, `AI/api/openai-completions.js:182`; the omlx custom `streamSimple` receives it in `options.apiKey`).
- true: `headers.Authorization = "Bearer <apiKey>"` is merged into `auth.headers` (`:221`), which `prepareRequest` merges into `options.headers` (`model-runtime.js:476`). Applies equally to the oauth, stored api_key and configured-key branches.
- true with no resolved key: throws `authHeader requires a resolved API key` (`:219-220`).

Stored oauth with empty `access`: `getApiKey` gives `""` (assuming omlx's `getApiKey` returns `access`, per the brief).
- `authHeader` true: `!auth.apiKey` is true for `""` -> throws inside `toAuth`; `resolveStoredOAuth` wraps it as `ModelsError("oauth","OAuth auth derivation failed for omlx")` with the cause (`resolve.js:117-122`). `prepareRequest` propagates the error; `ModelRegistry.getApiKeyAndHeaders` maps the cause message to `No API key found for "omlx"` (`model-registry.js:52-60`). No env fallback.
- `authHeader` false/unset: resolves successfully to `{auth:{apiKey:""}, source:"OAuth"}`; no header added; `options.apiKey = providerOptions.apiKey ?? ""` -> `""` (`model-runtime.js:487`). Request proceeds with an empty key.
- Availability/"configured" status for a stored oauth is decided only by credential type, not by `access` (`AI/models.js:274-277`: `{source:"OAuth",type:"oauth"}`). An empty-access oauth credential counts as configured.
- Expiry: the five-minute check uses `expires`; an expired credential calls `refreshToken` (`resolve.js:104-116`). (Empty `access` does not by itself trigger refresh.)

### 2. Request base URL

- `ModelRuntime.prepareRequest`: `requestModel = resolution.auth.baseUrl ? {...model, baseUrl: resolution.auth.baseUrl} : model` (`model-runtime.js:472`); the same in pi-ai `Models` (`AI/models.js:448`). So a per-credential URL can enter only through `ModelAuth.baseUrl` (`AI/auth/types.d.ts:6-10`; comment at `:233-236` "Covers per-credential baseUrl (GitHub Copilot)" for native `OAuthAuth.toAuth`).
- For the legacy extension oauth, `adaptOAuth.toAuth` returns only `{apiKey}` (`provider-composer.js:213`) and `withConfiguredAuth` spreads `...auth` without adding a URL (`:223`). **A `baseUrl` field in the stored oauth credential is never read by pi for requests** on this registration form. The stored credential is passed through verbatim (login/refresh keep extra fields, `:210,:212`) and is visible to `getApiKey`, `refreshToken`, `modifyModels`, and `refreshModels` (as `context.credential`), but pi itself never turns it into a URL.
- Otherwise the URL is `model.baseUrl`. Model `baseUrl` for an extension provider is computed in `extensionModelFromDefinition`: `definition.baseUrl ?? config.baseUrl ?? defaults?.baseUrl` (`provider-composer.js:139`), where `config` is the extension registration; with no `models` list, `applyExtension` overwrites every model's baseUrl with the registered provider `baseUrl` (`:190-192`). `applyModelsJson` (models.json) runs first: `config.baseUrl ?? model.baseUrl` (`:168`), and the extension layer is applied on top (`getAllModels`, `:357`). So precedence for a model's URL: model-level in extension `models` entry > extension provider `baseUrl` > models.json provider `baseUrl`/builtin. Provider-level `provider.baseUrl = extension?.baseUrl ?? config?.baseUrl ?? base?.baseUrl` (`:396`), and that value is passed to `refreshModels` as `context.baseUrl` (`AI/models.js:178`).
- `modifyModels` on the oauth block: pi does read it. After `refreshModels` runs with an oauth `context.credential`, the update callback sets `extensionOAuthCredential` (`provider-composer.js:411,422`); `getAllModels` then replaces chat models with `extension.oauth.modifyModels(chatModels, credential)` (`:358-364`), so an adjusted `baseUrl` on the returned models does become part of the catalog models that sessions use. Caveats: it is applied only after a `refreshModels` publish (the presence of `modifyModels` is what installs a `refreshModels` wrapper, `:402-403`); it is skipped when the context credential is not oauth (`:411`); and it is described as a "legacy synchronous credential-dependent model projection" (`types.d.ts` oauth block; `CHANGELOG.md:1631`). Models that a caller already holds are not rewritten; the request-time override is `model.baseUrl` from the object passed to `streamSimple` (`model-runtime.js:472`).

### 3. What an extension can read

- `ctx.modelRegistry` (`types.d.ts:245`, class `model-registry.js:6-140`): `getProviderAuthStatus(provider)` (`:63`; sync, from runtime snapshot: runtime key -> `"runtime"`; stored -> `"stored"`; configured `apiKey` -> `models_json_*`/`"environment"`/`"fallback"`; else check result; `model-runtime.js:448-458`), `isUsingOAuth(model)` (`:113`; sync, snapshot `auth.get(provider).type==="oauth"`, `model-runtime.js:360-362`), `getProviderAuth(provider)` (`:102`, async, returns `{auth:{apiKey,headers,baseUrl},env,source}` or `undefined`; same `resolveProviderAuth` path as requests, so it reflects exactly the credential pi will use; may throw), `getApiKeyAndHeaders(model)` (`:34`, never throws; returns `{ok,apiKey,headers,baseUrl?,env}` or `{ok:false,error}`), `getApiKeyForProvider(provider)` (`:105`, swallows errors), `hasConfiguredAuth(model)` (`:31`), `getProvider(id)` (`:66`), `getRegisteredProviderConfig` (`:134`), `refresh(options)` (`:12`).
- Not on `ModelRegistry`: `listCredentials`, `getAuth`/`checkAuth`, `login`/`logout` exist on `ModelRuntime` (`model-runtime.js:310,369,445,582-596`); no evidence the extension context exposes the runtime itself.
- `readStoredCredential(providerId, authPath?)` is exported from the package root (`PI/dist/index.d.ts:4`; `auth-storage.js:425-433`): synchronous one-off read of `auth.json` (default `getAgentDir()/auth.json`), returns `undefined` on any error; raw credential, no env interpretation, ignores runtime keys. CHANGELOG `:1627` names it as the SDK replacement for `AuthStorage`.
- `refreshModels(context)` gets `context.credential`, `stored`, `publish`, `allowNetwork`, `force`, `signal`, `baseUrl` (`AI/models.d.ts:15-36`; call at `AI/models.js:168-179`). `credential` is: the raw stored credential in the cache-only phase 1 (`allowNetwork:false`, `models.js:196-200`); in the network phase, for stored oauth the (refreshed) stored credential including extra fields (`models.js:246-256`), and otherwise a **resolved** `{type:"api_key", key, env}` built from `apiKey.resolve` (stored key, or configured/env key) (`:257-264`). If nothing resolves (no apiKey method, or none configured), the network phase is skipped, so `refreshModels` is not called with network allowed (`:239-242`; `:187`). If the registration has an `apiKey` that cannot be interpolated, the resolve throws and the refresh records an error for the provider (`:215-221`).
- Documentation: `docs/extensions.md:1216-1218` documents `ctx.modelRegistry.getProvider` / `getProviderAuth`; `:1222-1224` documents `streamSimple`/`complete`; `:1980-1982, :2094` document `refreshModels` incl. `context.credential/stored/publish/signal` (the credential/stored-catalog/network/signal context). `docs/custom-provider.md:155-160` documents `refreshModels` contracts. Not found in either doc: `readStoredCredential`, `getProviderAuthStatus`, `isUsingOAuth`, `getApiKeyAndHeaders` (grep of `docs/` and README returned only the `getProviderAuth` hit); `modifyModels` is documented only in the type comment (`types.d.ts` oauth block) and CHANGELOG (`:1631`, `:4240`), not in `docs/extensions.md` or `custom-provider.md` (grep of `docs/*.md` returned no `modifyModels` hit). `docs/custom-provider.md:135-141` says only that OAuth providers appear in `/login` and credentials are stored in auth.json.
- Extension events: `ExtensionEvent` union (`types.d.ts:1101`) contains no login/logout/credential event. Related events: `session_start` (`docs/extensions.md:473`, reasons startup/reload/new/resume/fork), `session_shutdown`, `model_select`, `before_provider_headers`/`before_provider_request`/`after_provider_response`.

### 4. Login and logout

- `/login` -> `loginProvider` -> `ModelRuntime.login` (`interactive-mode.js:5421-5433`, `model-runtime.js:582-589`): runs the provider's login method (`AI/models.js:365-411`; for legacy oauth the `adaptOAuth.login`, `provider-composer.js:200-211`), writes the credential to the store under the lock (`models.js:382-386`), then `synchronizeCredentialState(...,"login")` (`model-runtime.js:404-423`): `recomposeProvider` (re-composes the provider from the stored extension registration; the extension's `register` is **not** re-invoked), `models.refresh({allowNetwork:false, providers:[id]})` (so `refreshModels` is called once, cache-only phase, with the new stored credential; no network call, and no network phase), `updateModelSnapshot`, `refreshProviderAvailability`. Then the interactive UI runs `completeProviderAuthentication` (default model selection, status, `interactive-mode.js:5200-5260`).
- `/logout` -> `ModelRuntime.logout` (`model-runtime.js:590-596`; UI `interactive-mode.js:5170-5190`): deletes the credential (`AI/models.js:413-421`; runtime override too, `runtime-credentials.js:47-51`), then the same `synchronizeCredentialState(...,"logout")`: recompose, cache-only `refreshModels` with `credential: undefined`, snapshot/availability update. Note that `recomposeProvider` resets nothing on the extension's side; `extensionOAuthCredential`/`refreshedExtensionModels` live in the composed provider closure and are recreated by recompose (`provider-composer.js:351-353`), so after logout/login the catalog returns to the registered model list until a publish occurs.
- Notification of the extension: none by event. The only observable hooks are the extension's own callbacks: `oauth.login` (runs during login), `refreshModels` (called with the new/removed `credential`, `allowNetwork:false`), and `oauth.refreshToken` (on expiry). I found no login/logout event in `types.d.ts` or `docs/extensions.md`.
- `/login` for an api_key (`interactive-mode.js:5333`) goes through the same `ModelRuntime.login(...,"api_key")`; for a legacy registration without a native api-key login this is the default secret prompt from `composeApiKeyAuth` (`provider-composer.js:255-259`), stored as `{type:"api_key", key}`; only reachable when `composeApiKeyAuth` returns a method (i.e. a `rawKey` exists, `:249`).
- Errors in the post-login sync surface as `CredentialSynchronizationError` ("Logged in to X, but local model state could not be synchronized") (`interactive-mode.js:5457-5460`; `model-runtime.js:16-27`). The credential is already committed by then.
- Startup: `ModelRuntime.create` -> `runtime.refresh({allowNetwork: refreshFromNetwork})` (`model-runtime.js:97-111`); extension registrations flush later via `registerProvider`, which re-composes and fires `void this.refresh({allowNetwork:false})` (`:672-690`), i.e. cache-only unless a later refresh allows network. `ModelRegistry.refresh(options)` (`model-registry.js:12`) is the public way for an extension to trigger another refresh (default `allowNetwork` is `PI_OFFLINE`-dependent, `model-runtime.js:610`).

### 5. Env-only case

- Nothing stored, `apiKey: "$OMLX_API_KEY"` registered: `resolveProviderAuth` step 5 -> `composeApiKeyAuth.resolve` -> `rawKey` template -> env value from the auth context (`configContextEnv`, `provider-composer.js:233-243`) or `process.env` (`resolve-config-value.js:71-73`); empty string counts as unset (`env?.[name] || process.env[name] || undefined`). Source label `"configured API key"` (`provider-composer.js:298`). With `authHeader` true the Bearer header is added (`:308`).
- `OMLX_API_KEY` unset: `check` returns `undefined` for a missing env name (`provider-composer.js:269-277`) so the provider is **not configured** (no available models, `AI/models.js:274-294`); `getProviderAuthStatus` yields `{configured:false}` (`configuredRequestAuthStatus`, `provider-composer.js:480-492`); a direct request `resolve` throws `Failed to resolve API key for provider "omlx" from environment variable: OMLX_API_KEY` (`:295`, `resolve-config-value.js:199-218`), wrapped as `ModelsError("auth","API key auth failed for provider omlx")` (`resolve.js:124-131`). `refreshModels` network phase: the same throw is recorded as a refresh error (`AI/models.js:215-221`).
- Keyless registration (no `apiKey`): `composeApiKeyAuth` returns `undefined` while `oauth` exists (`provider-composer.js:249-250`), so only the oauth method exists; env cannot ever supply a key; the provider is configured only by a stored oauth credential (`models.js:274-277`). A stored api_key is rejected (see §1). If neither `apiKey` nor `oauth` exists, composition throws `no authentication method configured` (`provider-composer.js:374-375`) and pi falls back to the base (`model-runtime.js:169-172`).
- Not-configured status marks: `markProvisionallyConfigured` marks a freshly registered provider as configured when a stored credential exists or `configuredRequestAuthStatus` says configured (`model-runtime.js:657-671`, using type "oauth" if `oauth && !apiKey` `:688`).

## Assumptions, Differences, and Unknowns

- Differences from the brief's wording: (a) pi does not read a credential's `baseUrl` for requests on this form (§2); (b) when a stored credential exists env is not consulted, and a stored api_key under the keyless (no `apiKey`) registration is ignored, not used (§1, §5); (c) `refreshModels`'s `context.credential` for the non-oauth case is the resolved key (stored, configured or env), not the raw stored credential, in the network phase (§3).
- Assumed omlx's `getApiKey` returns `access` and `authHeader` value as the brief states; omlx source not read (Eleanor's scope). Empty-access behavior depends on the registered `authHeader` value (§1 gives both).
- Unknown/unverified: whether an already-selected session model is replaced by the `modifyModels`-adjusted model object after login (only `streamFn` -> `streamSimple(model,...)` was traced, `sdk.js:261-271`); no test run of any of this (static reading of 1.5.2 `dist` only); whether `ctx.modelRegistry` handed to extensions is always this `ModelRegistry` class (typed so at `types.d.ts:245`); `before_provider_headers` semantics not examined as a credential source.
- No login/logout extension event exists in 1.5.2 per `types.d.ts:1101`; checked docs by grep, not exhaustively read.

## Addendum 1 — unregister then register

Paths: `D` = `…/pi-coding-agent/dist/core`, `AI` = `…/pi-ai/dist`. Static reading, 1.5.2.

**Path (both cases).** `pi.unregisterProvider`/`registerProvider` → `applyRuntimeChange` runs the change immediately once the extension is no longer `loading` (`D/extensions/loader.js:206-211,371-384`). After bind, `runtime.*` calls `providerActions` (`D/extensions/runner.js:309-329`) → `AgentSession` (`D/agent-session.js:2944-2955`) → `ModelRuntime.unregisterProvider` then `registerProvider`, each followed by `_refreshCurrentModelFromRegistry` (`agent-session.js:2827-2837`). Pre-bind, they only edit the pending queues (`loader.js:170-180`), so unregister cancels the queued registration.

**Per call, all synchronous.**
- `unregisterProvider` (`D/model-runtime.js:691-697`): deletes the `extensionProviders` entry, calls `recomposeProvider` (`:144-153`). With no models.json overlay and no extension, `composeProvider` returns `base` (`:156-163`), which is undefined for omlx, so `models.deleteProvider("omlx")`. It then updates the snapshot and fires `void this.refresh({allowNetwork:false})`.
- The session hook then calls `getModel` → undefined → early return (`agent-session.js:2832-2834`). The selected model object is kept, not cleared and not thrown.
- `registerProvider` (`model-runtime.js:672-690`): validates, then `previous = extensionProviders.get(id)` is now undefined (`:679-680`). **The merge of the previous registration is cleared**: keys omitted or undefined in the new config (e.g. a keyless config without `apiKey`) are not inherited. A bare re-register would inherit them. It recomposes, re-marks provisional configured status (`:688`), and fires another `refresh`.
- The session hook then finds the new model object and sets `agent.state.model` (`agent-session.js:2833-2836`). The selection survives by `provider/id`, as a new object.
- No `await` sits between the two calls, so nothing observes the gap in the catalog. Composed closure state (`refreshedExtensionModels`, `extensionOAuthCredential`, `provider-composer.js:351-353`) is lost until the cache-phase `refreshModels` re-publishes with the stored credential (`AI/models.js:196-200`). auth.json is untouched.

**(a) Inside `oauth.login`.** `ModelRuntime.login` queues under `enqueueCredentialOperation` (`model-runtime.js:582-589`). `Models.login` looked up the provider before running the callback (`AI/models.js:366-376`), so the in-flight login completes on the old provider object. Registration is not in that queue, so it does not block or abort the login. The credential is then persisted (`models.js:382-386`), and `synchronizeCredentialState` calls `recomposeProvider` (`model-runtime.js:404-411`), which reads the **new** `extensionProviders` entry. The login survives and lands on the new registration. Caveat: the two unqueued `void refresh()` calls run a full `rebuildProviders` (`:597-610`) concurrently with that sync. I did not trace whether `clearProviders` aborts an in-flight refresh, so a transient sync error (`CredentialSynchronizationError`) is possible but unverified.

**(b) Background poll.** Same synchronous swap; the selected omlx model survives as a replaced object. An in-flight request keeps its old model object, and a request already past `prepareRequest` is unaffected. The next request resolves auth against the new composition. Cost: two extra refreshes per poll, and `refreshModels` oauth state is reset.
