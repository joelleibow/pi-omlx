## 4. The singleton guard — Joel's

Mechanics re-checked: pi dedups extension entries by resolved path only (`dist/core/extensions/loader.js:676-684`); `Symbol.for("pi-omlx/loaded")` is shared across module instances; the only path that fires the early return is the extension installed twice in one process (global `packages` plus a project `.pi/settings.json` or `.pi/extensions` copy). Joel's own setup has one install (`~/.pi/agent/settings.json` → `../../Projects/pi-omlx`; this repo's `.pi/` has no `settings.json`). The upstream `extension_load_skipped` trace was lost in `52183fd`, so today the skip is silent. Without the guard a dual install would: register `omlx` twice (pi merges the second over the first, ADR 0001), run two poll loops, apply `applyOmlxThinkingControls` twice (idempotent — same keys, same values), and show two warnings.

**What Joel decides:** when pi loads pi-omlx twice in one process, is the second copy silently skipped (today), or does it run like any other pi extension (merged re-registration, two polls, two warnings)? **Evidence he needs:** a dual install measured under pi 1.5.2 with the guard present and removed — `/model` list, count of `provider_registered` lines, count of warnings, whether `/login` or `/logout` behaves differently. **What I would choose:** delete the guard, the key and the `session_shutdown` clear. The trigger is a configuration mistake nobody has made; the guard hides it instead of surfacing it; and if dedup is wanted as product behaviour it needs the lost trace restored and a test that drives the factory twice — that is new mechanism, not deletion. If Joel rules dedup stays, the card adds that test and the trace, and the design gate holds both.
