## Measurements (scratch-michael, in-process factory with a fake pi, stored credential pointing at a TCP server that accepts and never answers)
- Cache present: factory resolved after **4011 ms**; cached models registered at 0 ms, re-registered at 4010 ms. Cache absent: **4010 ms**, login-only at 0 ms and again at 4009 ms. Connection refused: 15 ms. This matches Eleanor's 4.15 s / 0.13 s through real `pi --list-models` — the whole delta is the extension.
- Why 4 s and not 2 s (Chidi's open item, answered from source): `getJson` rewraps the AbortError as a plain `Error("GET … timed out …")` (`catalog.ts:363-364`), so `fetchModels`'s `err.name === "AbortError"` check at `:227` never matches and a status timeout **falls through to `/models`**, which times out again. Traced: `catalog_status_failed` at 2006 ms, throw at 4009 ms. **Eleanor's report says the opposite** ("AbortError … is rethrown, so timeout does not use /models fallback"); that sentence is wrong and Bambadjan must not lean on it. Global-settings is a third request only when a parsed model lacks limits, so an unreachable server costs two timeouts, not three.
- Why cache didn't change the duration: the cached registration never gated the await; it only ran before it.

## Traps
1. **There are already two startup fetches.** The awaited one (`:57`) and the poll's immediate first iteration (`:101-104`, no sleep before the first `refreshProvider`). Dropping only the `await` makes them **concurrent**: two fetches, two cache writes, two registrations, and the race decides which `state`/registration wins. The minimal correct change is to delete the startup refresh (`:57-60`) and let the poll's first tick be the startup fetch; that changes neither interval nor backoff. (Design choice, mine to gate; I state my preference below.)
2. **pi picks the initial model right after extensions load.** `sdk.js:78-81` awaits `resourceLoader.reload()` (which awaits every factory, `loader.js:523`), then `findInitialModel` (`sdk.js:104`) reads the snapshot. Today the 4 s buys a populated omlx catalog at that moment when the server is up. Without the wait and **without a cache**, `getModel("omlx", default)` is undefined, so pi silently falls to another provider's first available model or "no models available" (`model-resolver.js:405-432`); `--continue` prints "Could not restore model omlx/… (model no longer exists)" and falls back (`:437-452`). The catalog then lands ~100 ms later and the user must `/model`. Late registration itself works: `registerProvider` after `commit()` applies directly and recomposes the snapshot (`loader.js:206-211`, `model-runtime.js:672-689`); the poll already relies on this. This consequence is the substance of the "deliberate" no-cache behaviour and is Joel's (below). Note the cache is keyed by `apiRoot`, so "no cache" also happens after every `/login` to a new URL, not only on first install.
3. **Nobody is ever told anything today.** `state.lastError` is read in one place, the login callback (`index.ts:135`); a failed or stale catalog produces no user-visible line. There is a mechanism available (`ctx.ui.notify`/`ctx.ui.setStatus`, `types.d.ts:91,95`, reachable from a `session_start` handler's ctx) but no decision asks for it yet.
4. **The cached-case test writes its fixture at `CACHE_FILE`'s actual path**, which is captured at import: `<isolation root>/agent/cache/omlx-models.json` (`inject("isolationRoot")`), **not** the per-test `dir` that `driveExtension` sets as `PI_CODING_AGENT_DIR`. Every successful-fetch test in `index.test.ts` already writes that same file, so the cached test must set its contents and the no-cache test must remove it; otherwise test order decides. Fixing the capture is the seam card's.
5. **Red-then-green shape for "not delayed":** a fetch fake that never resolves (or resolves only when the signal aborts) under `vi.useFakeTimers()`; `await extension(pi)` must resolve with the cached models registered **without advancing timers**. On today's code that test hangs → red. A test that advances timers past 4 s would stay green either way and proves nothing.
6. **`index.test.ts` assumptions move:** `settle()`'s comment and `fetches[0]` being "the startup fetch", and the poll test's `beforePoll + 1` count, are re-derived once the startup fetch is the poll's first tick (or made concurrent). `STARTUP_TIMEOUT_MS` (`:28`) also feeds the poll (`:103`); its name becomes false when the startup wait goes — rename if touched, but the 2 s per-request value itself is not interval or backoff and nothing asks to change it.
7. **Scratch discipline:** every bash call starts in the repo; `git status --short` after each research run (clean now: only `.pi/` and the change dir untracked).

## Settled vs open
- **Settled:** the silent startup wait is removed; cached case = register from cache synchronously, no wait (already how `:56` works once `:57-60` go); tests per case inside the isolation; no new seams; nothing on the deferred list moves; interval/backoff untouched.
- **Open for the council / Bambadjan (I gate at PL4):** whether the startup refresh is deleted in favour of the poll's first tick (I'd choose delete — smallest diff, removes the double fetch, keeps interval and backoff); the test shapes above; what the design says about re-registration after a failed fetch now that `:60` and `:110` are the same behaviour in two homes.
- **Open for Joel (product):** (a) the no-cache behaviour as the user sees it — I'd choose: start login-only, catalog lands when the fetch does, user picks via `/model`, and document that a saved default omlx model is not selected on a session that starts without a cache; the alternative, waiting only when there is no cache, is a bounded silent wait and contradicts his ruling unless he explicitly accepts it. (b) **Indication.** His words condemn the wait *because* it was silent; the recorded decision ("must not wait … without the user being told") forbids a silent wait, it does not require a notice in a no-wait world. So a runtime notice is **not settled by his words; it is his to rule.** My view: one `ctx.ui.notify` warning on the session's first failed catalog fetch ("OMLX catalog unreachable at <url>; using N cached models" / "login-only") closes the same class of silence he objected to, since trap 2 and trap 3 otherwise leave the user on another provider's model with no line saying why. Without his ruling, a notify is mechanism nobody asked for and I would not pass it at PL4.
