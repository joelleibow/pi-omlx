Labels: **[src]** read installed `dist/` source, **[doc]** installed docs, **[exp]** ran an experiment (scratch `.pi/marbleization/stop-blocking-startup-on-the-model-fetch/scratch-chidi/`; `HOME`/`PI_CODING_AGENT_DIR` set to scratch, `PI_OFFLINE=1`, `env -i`; extension `ext.ts` registers `early/e1` in the factory and `late/l1` from a `setTimeout`).

## 1. What pi awaits from an extension factory

- **[src]** `PI/dist/core/extensions/loader.js` `initializeExtension()`: `await factory(load.api); load.commit();`. `loadExtensionsInternal()` loads extension paths **sequentially** (`for … await loadExtension`), so a slow factory delays later extensions too. A throw/reject discards the extension's registrations (`load.discard()`) and surfaces as "Failed to load extension".
- **[doc]** `docs/extensions.md` L213: "If the factory returns a Promise, Pi awaits it before continuing startup … completes before `session_start`, before `resources_discover`, and before provider registrations queued via `pi.registerProvider()` are flushed." `docs/custom-provider.md` L21 says the same and states providers registered there are "available to startup model selection and `pi --list-models`".
- **[doc]** `docs/extensions.md` L254-256: "Extension factories may run in invocations that never start a session. Do not start background resources such as processes, sockets, file watchers, or timers from the factory. Defer … until `session_start` … Register an idempotent `session_shutdown` handler."
- **[src]** Order (`dist/main.js` `createRuntime`, ~L640-760; `core/agent-session-services.js` `createAgentSessionServices`):
  1. `ModelRuntime.create(...)` (builtins + `models.json`; `allowModelNetwork` not set, so no network at create).
  2. `resourceLoader.reload()` → **extension factories run and are awaited here**.
  3. Pending provider registrations (made during the factory) are flushed into `modelRuntime`; then `modelRuntime.refresh({ allowNetwork: false })`.
  4. `resolveModelScope`, `buildSessionOptions` (`--model` resolved via `resolveCliModel`), `createAgentSessionFromServices` → `createAgentSession` (`core/sdk.js` L80-110) picks the initial model (session restore, else `findInitialModel`).
  5. After the runtime exists: `--list-models` prints and `process.exit(0)` (`main.js` ~L776); otherwise the mode starts.
  6. `session.bindExtensions()` (`agent-session.js` L2756) → emits `session_start` (`reason:"startup"`) → `resources_discover`. Print mode: `modes/print-mode.js` L60; RPC: `rpc-mode.js` L234; interactive: `interactive-mode.js` L1586 inside `init()`.
- **Modes.** Every mode (interactive, `-p`/json, `--list-models`, `--help`, RPC) runs steps 1-4 before anything else, so the factory's await is on the critical path in all of them.
  - **Interactive [exp]:** with a 3000 ms factory delay, `tmux capture-pane` at t=1.5 s showed a **blank terminal**; the TUI header appeared only after factory end (~3.2 s). The TUI is built after `createRuntime` (`interactive-mode.js` L725-740 "Start the UI before initializing extensions" refers to `session_start`, not to factories). No pi-side indication is shown while a factory is pending.
  - **`-p` [exp]:** factory 120 ms → `session_start` at +10 ms (`hasUI=false mode=print`).
  - **RPC [exp]:** factory end 627 ms → `session_start` 652 ms (`hasUI=true mode=rpc`).
  - **`--list-models` [exp]:** `FACTORY_DELAY=1500` → process took ≥1.67 s before printing; factory log "end" at 1666 ms.
- **Factory run count [exp]:** in `-p`, `--list-models`, RPC and TUI runs the factory logged **once** per process despite `main.js` L799 `resourceLoader.reload()` for non-interactive modes (a reload there did not produce a second factory-start log line). `session_shutdown` fired once, at exit. (`/reload` and `ctx.reload()` re-run factories by design: docs `session_shutdown` reason `"reload"`; not exercised.)
- **Models available at the time `session_start` fires:** anything registered during the factory, nothing registered later (see §2).
- **Timeouts pi imposes:** `createAgentSessionServices` is passed `modelRuntimeSignal: AbortSignal.timeout(15_000)` (`main.js` ~L663) but that bounds `ModelRuntime.create`, not extension factories. No timeout wraps `await factory(...)` **[src]**.

## 2. Registering a provider after the factory returned

- **[doc]** `docs/extensions.md` L1978: "Calls made during the extension factory function are queued and applied once the runner initialises. Calls made after that … take effect immediately without requiring a `/reload`." `custom-provider.md` L122 same.
- **[src]** Pre-bind `registerProvider` pushes to `runtime.pendingProviderRegistrations` (`loader.js` L170); `AgentSession` binds `registerProvider: (name, config) => { modelRuntime.registerProvider(...); this._refreshCurrentModelFromRegistry(); }` (`agent-session.js` L2944). `_refreshCurrentModelFromRegistry()` (L2827) only re-fetches **the currently selected model by provider/id** and swaps in the new object if it differs; it never selects a different model.
- **Late registration is visible to model APIs [exp]:** RPC: `late/l1` registered at 1629 ms appeared in `get_available_models` queried at ~3 s (`early/e1,late/l1`); `--list-models` printed `late l1` when the timer fired before the listing completed (race; timer fires only when the event loop yields).
- **Saved default not yet registered at startup [exp + src]:** `settings.json` `{"defaultProvider":"late","defaultModel":"l1"}` with `late/l1` registered after the factory: pi **silently fell back** to the first available model (`early/e1`) in `-p`, RPC (`get_state`), and TUI (footer showed `e1`). No error, no `modelFallbackMessage`; it stays on the fallback after `late/l1` appears (RPC `get_state` at ~3 s still `early/e1`). Source: `findInitialModel` (`core/model-resolver.js` L390-436) step 2 requires `modelRuntime.getModel(defaultProvider, defaultModelId)` and configured auth, else step 3 "first available model with valid API key", silent. `modelFallbackMessage` is set only when there is no model at all (`sdk.js` `formatNoModelsAvailableMessage`) or a **session** model could not be restored (`Could not restore model …`).
  - If nothing else is available, interactive mode starts without a model; non-interactive modes print the no-models message and `process.exit(1)` (`main.js` ~L809).
  - Resumed session whose saved model is missing: `sdk.js` sets `modelFallbackMessage = "Could not restore model <p>/<id>"` then falls back (`Using <p>/<id>`). **[src]** only.
- **`--model late/l1` [exp]:** `Error: Model "late/l1" not found. Use --list-models to see available models.` exit 1 (resolved in `buildSessionOptions` at step 4, before any late registration). `--model early/e1` (factory-registered) resolves.
- **Selection is one-shot.** Nothing in pi re-runs default-model resolution when a provider appears later **[src: only `_refreshCurrentModelFromRegistry`]** and **[exp]** above. An extension can switch with `pi.setModel(model)` (docs L1942: recorded in session history, does not change `defaultProvider`/`defaultModel`; returns `false` if auth not configured).
- **Cached-then-fresh models.** Re-registering the same provider name with a different model list while a session is using one of its models: `_refreshCurrentModelFromRegistry` swaps the model object for the same id; if the id vanished it returns without change (current model object stays) **[src]**.

### Events/APIs usable after startup
- **[doc/src]** `session_start` (`reason: startup|reload|new|resume|fork`; handlers receive `ctx` with `ctx.ui`, `ctx.hasUI`, `ctx.mode`, `ctx.model`); `session_shutdown`; `model_select`; commands/tools/event handlers; `pi.registerProvider`/`unregisterProvider` any time after load (`assertActive()` guard: a captured `pi`/`ctx` becomes **stale after reload or session replacement** and throws; `loader.js` L151).
- **`refreshModels` hook [doc + src + exp]:** `pi.registerProvider(name, { ..., refreshModels(ctx) })`; context keys observed **[exp]**: `credential, stored, publish, allowNetwork, force, signal, baseUrl`. Docs: returned models replace the extension-provided list; `context.signal` must be honoured. Observed call pattern (RPC): several calls **before** `session_start` with `allowNetwork:false`, then one `allowNetwork:true` call right after `session_start`, then another call after each late `registerProvider`. In `-p` and `--list-models` runs `refreshModels` was **not called at all** [exp].
- **Who triggers network refresh [src]:** RPC: `main.js` L821-826 background `modelRuntime.refresh({signal})` with 15 s timeout, errors swallowed. Interactive: `InteractiveMode.run()` (L861-869) after `init()`: `refreshModelCatalogs(modelRuntime, signal)` with 15 s abort, `.catch(() => {})` (errors swallowed, no UI), then `updateAvailableProviderCount()`; skipped when `PI_OFFLINE` set. Print/json/`--list-models`: no network refresh; `ModelRuntime.refresh` defaults `allowNetwork` to `modelNetworkEnabled` (`PI_OFFLINE === undefined`) but pi calls it only with `allowNetwork:false` in those modes.
- **No model-registry change event** is exposed to extensions in the docs (`grep` of `extensions.md` event list: `model_select` only fires on selection; `mcp_servers_change` is MCP). **Gap:** I did not enumerate every `ExtensionAPI` event type in `types.d.ts`; none named like "models_changed" was seen in docs.

## 3. Telling the user something is happening / failed

- **Interactive [exp]:** `ctx.ui.notify(msg, "warning")` called in `session_start` rendered a line `Warning: <msg>` above the editor; `ctx.ui.setStatus("key","text")` rendered `text` on the footer's extension-status line (second footer line), persistent until `setStatus(key, undefined)`. Also available [doc `extensions.md` ~L2885-2925]: `setWidget` (above/below editor), `setFooter`/`setHeader`, `setWorkingMessage`, `setTitle`, dialogs (`select/confirm/input/editor/custom`).
- **Print / json mode [src]:** `bindExtensions` is called without a `uiContext`, so `ctx.ui` is `noOpUIContext` (`core/extensions/runner.js` L132): `notify`, `setStatus`, `setWidget` etc. are **silent no-ops**, dialogs return `undefined/false`. `ctx.hasUI === false` (docs L1177: "true in TUI and RPC modes. false in print mode (-p) and JSON mode"). Anything an extension wants on a non-interactive run must go through `console.error`/stderr (not tested whether pi swallows stdout in print mode: `takeOverStdout`/`restoreStdout` exist in `main.js`; stdout is redirected to stderr during non-interactive runs per `takeOverStdout`, **[src] not re-verified**).
- **RPC [src]:** `rpc-mode.js` `createExtensionUIContext`: `notify` and `setStatus` emit `{"type":"extension_ui_request","method":"notify"|"setStatus",…}` JSON lines on stdout; `setWidget` (string-array only), `setTitle` likewise; `setFooter`, `setWorkingMessage` etc. are no-ops; dialogs round-trip. `ctx.hasUI` is true.
- **Before `session_start`:** no UI context exists yet, so **a factory cannot call `ctx.ui`** — only `console.*`. In interactive mode the terminal is still blank while the factory runs [exp]. `pi.ui` does not exist on `ExtensionAPI`; `ctx` is only passed to event/command/tool handlers.
- **Pi's own channel for load problems:** a throwing factory yields a diagnostic `Failed to load extension "<path>": <msg>`; `main.js` prints diagnostics (interactive: startup diagnostics block; non-interactive: stderr) and **exits 1 on runtime errors** (`hasRuntimeErrors` → `process.exit(1)`, plus `EXTENSION_LOAD_FAILURE_HINT`). Provider-registration errors at flush are reported as `Extension "<path>" error: <msg>` (error-type diagnostics, also fatal in non-interactive).
- **Examples:** `examples/extensions/notify.ts`, `status-line.ts`, `model-status.ts`, `working-message-test.ts`, `titlebar-spinner.ts` demonstrate these APIs (not opened line by line).

## 4. How built-ins and examples handle network discovery

- **Built-in remote catalog (pi's own pattern) [src]** `PI/dist/core/remote-catalog-provider.js` `withRemoteCatalog`: `refreshModels(context)` first **publishes the persisted snapshot** (`context.stored`) synchronously, then `if (!context.allowNetwork || context.signal.aborted) return;`, skips the request if checked within `REMOTE_CATALOG_REFRESH_INTERVAL_MS` (unless `context.force`), uses etag/`if-none-match`, passes `context.signal`, and persists via `context.publish({ persist })`. Startup uses `allowNetwork:false` (cache only); network refresh runs in the background (RPC/interactive) with a 15 s abort. `docs/custom-provider.md` L160-162: "A live service such as llama.cpp can update its in-memory list without persisting it; a remote catalog can retain a snapshot for offline startup."
- **Docs' own example for live discovery** (`extensions.md` L2036-2050): `refreshModels({ signal })` with `fetch(url, { signal })` (llama.cpp). **Contrast** with the "Async factory functions" example (L217-250), which does an un-timed `await fetch()` in the factory and is documented as making models available at startup and to `--list-models`; docs add "For model lists that change while Pi runs, implement `refreshModels` instead."
- **`ModelRuntime.create`** (`core/model-runtime.js` L79-115): the pi-side startup refresh takes an `AbortSignal`, optional `modelRefreshTimeoutMs`, and `allowModelNetwork`; the CLI passes `allowModelNetwork` false at create for every mode, and `PI_OFFLINE` disables network entirely.
- **Examples directory** (`PI/examples/extensions/`): `custom-provider-anthropic/`, `custom-provider-gitlab-duo/` (static model lists; GitLab fetches at stream time), `dynamic-tools.ts`, `dynamic-resources/`. No example found that blocks the factory on a network call besides the docs snippet. Not read in full.

## Differences from the card's assumptions
- Card says startup is delayed by the factory await: confirmed for **all** modes, and interactive shows a blank screen with no pi-provided indication [exp].
- No-cache + late registration: pi neither errors nor retries default-model selection; a saved `defaultModel` belonging to the late provider silently resolves to another model [exp].
- `ctx.ui` is unavailable in the factory and a no-op in print mode.

## Addendum 3 (Chidi): /new, /resume, /fork, /reload in pi 1.5.2

`PI` = `/Users/joelleibow/.local/share/fnm/node-versions/v26.8.1/installation/lib/node_modules/@earendil-works/pi-coding-agent/dist`. [src] = read source, [exp] = ran experiment (scratch-chidi/ext3.ts, RPC/print/json, isolated HOME and `env -i`).

### 1. Which re-run the factory (after `session_shutdown`) vs. only fire `session_start`
**All four re-run the factory and emit `session_shutdown` first. None only fires `session_start` on the existing instance** (only the first startup fires `session_start` on a freshly loaded instance).
- `/new`, `/resume`, `/fork` (and import): `PI/core/agent-session-runtime.js` `newSession` L147-171, `switchSession` L128-146, `fork` L174-250. Each calls `teardownCurrent(reason, target)` (L102-113: `session.abort()`, emit `session_shutdown` with `reason` "new"/"resume"/"fork" and `targetSessionFile`, then `session.dispose()`, which calls `runner.invalidate()` at `agent-session.js` L1081), then `this.createRuntime({... sessionStartEvent:{type:"session_start", reason, previousSessionFile}})` (L161, L137, L207/225/242). `createRuntime` is the same closure as startup (`main.js` ~L644-765: `createAgentSessionServices` → new `DefaultResourceLoader` → `resourceLoader.reload()` → factories awaited, as in §1 of the main report). The new session's `session_start` is emitted by `bindExtensions` (`agent-session.js` L2756-2776) via `finishSessionReplacement` → `rebindSession`.
- `/reload` (`ctx.reload()`, interactive `handleReloadCommand` `interactive-mode.js` L5501, print/RPC call `session.reload()`): `agent-session.js` `reload()` L3094-3135: `emitSessionShutdownEvent(oldRunner, {reason:"reload"})`, `oldRunner.invalidate()`, `await this._resourceLoader.reload()` (factories re-run), `_buildRuntime` (new `ExtensionRunner`), then, only if UI/command/shutdown/error bindings exist, emits `session_start` with `reason:"reload"`. Same `AgentSession` object, new runner and new extension instances.
- [exp] `/new` via RPC `new_session`: log order `session_shutdown new` (1511 ms) → `factory` (1522) → `session_start new` (1533).
- Consequence: extension module-level state persists across these (same process, jiti cached module), but anything the factory creates (closures, `pi` object, `ctx`) is new, and the old `pi`/`ctx` are stale (see §4). Anything global the factory set (e.g. `globalThis[Symbol.for(...)]`) survives unless `session_shutdown` clears it.
- RPC quirk [exp + src]: after `new_session` the `session_start new` handler ran **twice** (logged twice, notify emitted twice) though the factory ran once: `rpc-mode.js` L356-360 calls `rebindSession()` explicitly while `runtimeHost.setRebindSession` (L305-ish; `finishSessionReplacement` in `agent-session-runtime.js` L121-126) already rebinds, and `bindExtensions` emits `session_start` each time. Not observed in print/interactive paths (not tested for interactive). Handlers must be idempotent.

### 2. Which re-run initial model selection
- `/new`, `/resume`, `/fork`: **yes**, via the same `createRuntime`: `buildSessionOptions` (re-applies CLI `--model`, `--models`/scoped models and saved default) then `createAgentSession` (`core/sdk.js` ~L80-110): if the session has messages, restore from the session's model entry (`modelRuntime.getModel` + `hasConfiguredAuth`; else `modelFallbackMessage = "Could not restore model p/id"`), else `findInitialModel` (`core/model-resolver.js` L390-436: scoped, saved default, first available with auth). A fresh `/new` session (no messages) therefore resolves `defaultProvider/defaultModel` again against whatever is registered **after the factory re-ran**, so a late-registered default would be picked up on `/new`, `/resume` (if the resumed session has no saved model), `/fork`.
- `/reload`: **no**. `reload()` L3094-3135 contains no model resolution (`grep findInitialModel|restoreModelFromSession` in `agent-session.js`: none; `sdk.js`/`model-resolver.js` only). The current model persists; provider re-registrations only trigger `_refreshCurrentModelFromRegistry` (L2827), which swaps the current model by provider/id.

### 3. `ctx.ui.notify` per mode
- **Interactive**: `showExtensionNotify` (`interactive-mode.js` L2403): `"error"` → `showError`, `"warning"` → `showWarning`, otherwise (info/undefined) → `showStatus`. [exp earlier] "warning" rendered as `Warning: <msg>` above the editor.
- **`-p` print mode and `--mode json`**: **silent no-op**. `print-mode.js` L60 calls `bindExtensions({mode: "json"|"print", ...})` with no `uiContext`, so `ctx.ui` is `noOpUIContext` (`runner.js` L132-; `notify: () => {}`), `ctx.hasUI === false`. [exp] `-p` and `--mode json`: timer-driven `ctx.ui.notify` did not throw (`timer300 ok`, `timer2500 ok`) and the text appeared on neither stdout nor stderr (`grep timer` = 0 in both).
- **RPC**: emits a stdout JSON line `{"type":"extension_ui_request","id":<uuid>,"method":"notify","message":...,"notifyType":"info|warning|error"}` (`rpc-mode.js` `createExtensionUIContext`, bundled in `bundle/chunks/chunk-VEJDBY3O.js`; [exp] captured `"message":"timer300 from startup","notifyType":"info"`). `ctx.hasUI` true; `setStatus` likewise emits `method:"setStatus"`.

### 4. Is the `session_start` handler's `ctx` usable after it returns (timer)?
- **Yes while that session/runner stays active; no after it is replaced or reloaded.** `ctx.ui` and other getters call `runner.assertActive()` (`runner.js` L626-683) which throws `state.staleMessage` once `runtime.invalidate()` ran (`loader.js` L117-121). `invalidate()` is called by `session.dispose()` (L1081; used for `/new`, `/resume`, `/fork`, import and quit teardown) and by `reload()` (L3104).
- [exp] RPC: timer scheduled in `session_start startup` with 300 ms and 2500 ms. 300 ms timer: `ctx.ui.notify` worked (emitted `extension_ui_request`). `new_session` at ~1.5 s; the 2500 ms timer from the old `ctx` **threw** `This extension ctx is stale after session replacement or reload. Do not use a captured pi or command ctx after ctx.newSession(), ctx.fork(), ctx.switchSession(), or ctx.reload()...` (2690 ms). The new session's own `session_start` ctx timers worked.
- The same staleness applies to a captured `pi` (`loader.js` L200-205 `assertActive` in every `pi.*` call, including `pi.registerProvider`): a timer or polling loop started by the first factory/`session_start` and still running after `/new` etc. throws on its next `pi`/`ctx` use unless it re-captures from the new `session_start` (or catches). Plain module-level code (fetch, state) keeps running; only API calls through the old `pi`/`ctx` fail.
- Not tested interactively (tmux) for `/new`/`/reload` staleness; source shows the same `invalidate()` path for the interactive runtime.
