== 2. Traps, measured ==

I ran the extension's own precedence (`loadConfig`, `resolveConfiguredApiKey`, `hasOmlxTarget`) under a scratch `PI_CODING_AGENT_DIR` for 4 stored shapes × 4 env states; Eleanor's matrix is correct cell for cell. Pi's side is read from source, not run.

(a) Base URL, not just key. Today both catalog and requests take the URL from `config.apiRoot` — one source — but `loadConfig` (`src/config.ts:18-22`) throws the stored URL away whenever `OMLX_API_KEY` is set: stored oauth {S,K} + env X → catalog D/X, registered baseUrl D, chat key K (stored shadows env). So the env key alone moves BOTH sides to the default server and splits the key. Joel's live state, measured from his real cache (`apiRoot` = `http://localhost:8000/v1` = his stored URL, not D): no env override is in effect in his running pi, so his break is latent; it is real for anyone exporting the key.

(b) Keyless server. Stored oauth with `access:""` + env X → extension registers `apiKey:"$OMLX_API_KEY", authHeader:true`; pi resolves the stored oauth (shadowing env), `getApiKey` → "", `withConfiguredAuth` throws `authHeader requires a resolved API key` → "No API key found for omlx" on every chat. Hard break, pre-existing. Also: `hasOmlxTarget`'s docstring says an env base URL alone signals a keyless server — pi disagrees. OMLX_BASE_URL only, nothing stored → extension registers keyless (oauth-only); `checkProviderAuth` (pi-ai `models.js:274-279`) and `configuredRequestAuthStatus` both say not configured; `resolveProviderAuth` returns undefined → "Provider is not configured: omlx". The env-only keyless user has never had working chat; only `/login` with an empty key does. The design must either drop that column or state it as a known-dead path.

(c) Env-only user (nothing stored, X set, optional E). Consistent today on both sides (pi's step 5 reads `$OMLX_API_KEY`). A design that makes the extension ignore env entirely breaks CI/ephemeral shells → §3.1.

(d) Stored `api_key` vs oauth. Correction to the brief's premise: Joel's dotfiles template (`dotfiles/home/dot_pi/private_agent/private_auth.json.tmpl:19-24`) writes `type:"oauth"` with `baseUrl`, `access`, `refresh:""` and NO `expires`; his live auth.json matches. Consequences: interactive pi is fine (`Date.now()+5min >= undefined` is false, so no refresh ever fires, and `AuthStorage.load` does not validate); `pi --no-refresh` uses `ReadOnlyAuthStorage` (`main.js:184`) whose validator (`auth-storage.js:203-210`) rejects a non-finite `expires` as "Invalid auth.json" — a dotfiles defect, not this change's, but it is the shape the design must read. A real `api_key` credential arrives only via `/login` → "Use an API key" (pi's default secret prompt, no `baseUrl`), reachable only while the registration carries `apiKey` (`:249`). With it stored and the extension keyless (no env key, `loadOmlxCredential` returns the key so keyless=false — fine); with an EMPTY stored key, `loadOmlxCredential` returns undefined → keyless registration → pi hits resolve.js:33 → not configured. Edge, acceptable to document.

(e) Re-registration merges. `ModelRuntime.registerProvider` (`model-runtime.js:674-686`) merges defined values over the previous registration and skips undefined ones. `toProviderConfig` omits `apiKey` when keyless, so a keyless re-registration after a keyed one KEEPS `apiKey:"$OMLX_API_KEY"` in the effective config; only `unregisterProvider` (used by `registerLoginOnlyProvider`, never by `registerModels`) clears it. A design that toggles keyless-ness across the poll loop by omission does not do what it reads as doing.

(f) Login mid-session. The login callback fetches and registers BEFORE pi persists (index.ts:138-154 comment, true per `models.js:382-386`). `keyless = !explicitApiKey && !resolveConfiguredApiKey()` (index.ts:165) therefore reads the OLD stored/env state: logging in with an empty key while env X or an old keyed credential exists registers `authHeader:true`, and the first chat after pi stores the new keyless oauth throws (b). The poll loop then re-derives from `loadConfig()` ≤10 min later and, with env X set, overwrites the login's URL with D. Rule the design needs: `keyless` is a property of the one credential being registered for, never of ambient state. pi fires no login/logout event (`types.d.ts:1101`); after login pi recomposes and runs a cache-only `refresh` — an extension `refreshModels`/`modifyModels` hook is the only notification, and adding one changes pi's composition (`provider-composer.js:402-403`) — that is new mechanism and goes through the design gate, not a fix.

(g) Logout mid-session. No event; `state.config`/registration stay as they were for ≤10 min; pi has nothing stored and `$OMLX_API_KEY` unset → models drop from `available` and a request throws "Provider is not configured". Next poll → `not_configured` → login-only provider. Acceptable if the design names it as a consequence.

(h) Catalog cache keyed by `apiRoot` (`src/catalog.ts:575-578`, strict equality, one file). Changing URL precedence changes Joel's `apiRoot` only if his stored URL stops being chosen; today it is chosen, so no churn for him. For a user whose URL flips (env↔stored), startup gets a cache miss → login-only provider until the 2 s fetch. Self-healing; state it.

(i) Tests and the seam. Measured: `readStoredCredential(providerId, authPath = join(getAgentDir(), "auth.json"))` evaluates `getAgentDir()` per call, and `getAgentDir()` reads `process.env.PI_CODING_AGENT_DIR` at call time (`config.js:510-516`). So a test can point the real read at a temp dir by setting that variable and writing `<tmp>/auth.json` — no seam, and it is the same isolation the `verification` spec already mandates. Caveat: `CACHE_FILE` (`catalog.ts:567`) is bound at import, so cache isolation still comes from the suite-level prefix, not per-test env. New tests for this change should take the env route; touching the existing `_setAuthPathForTesting` call sites is the other card's work.

(j) Don't fix it in the transport. The extension's `streamSimple` wrapper receives pi's resolved `options.apiKey` and `Authorization` header; it could overwrite them with the catalog's key. That puts credential policy in `stream.ts` and fights pi's `authHeader`. I would refuse it at PL4.

(k) Minor: `applyStoredCredentialToEnv` and `readLastCatalogCache` have no callers outside tests (`rg` over non-test files) — dead exports the change will trip over; deletion, not preservation, if the design touches `config.ts`.

== 3. Calls that are certainly Joel's ==

1. Do `OMLX_API_KEY`/`OMLX_BASE_URL` keep any role once a login is saved? Pi has already decided its half: a stored credential owns requests and the extension cannot change that (no runtime API exposed). So the only way to satisfy §1 is for the extension to adopt pi's rule — stored owns both URL and key; env consulted only when nothing is stored. Cost: `docs/CONFIGURATION.md:21-24`'s "env overrides the stored login" contract is withdrawn (it was already false for chat), the two config tests titled "does not mix…" invert, and a user who wants a per-shell override must `/logout` first. The alternative — keep env as an override — is unimplementable without putting policy in the stream wrapper (j). My choice: stored owns; env is the fallback for the no-login (CI) case only. This is a user-facing contract, so it is his.
2. Does env survive at all? Removing env entirely is smaller code but breaks the env-only CI user (c) and `.env.example`. My choice: keep env as the no-credential fallback; it costs nothing because pi's step 5 already reads `$OMLX_API_KEY`.
3. Is the env-only KEYLESS column (OMLX_BASE_URL alone, no login) in scope? It has never worked for chat (b). Fixing it needs a way to make pi treat a keyless provider as configured without a stored credential — I found none in 1.5.2 short of the extension writing a credential, which revises the archived "this repo writes no credentials" record. My choice: out of scope, documented as "/login with an empty key".
4. Does this change touch the seam-dependent tests? §3 ruling says the seam card is separate; new tests go the env route (i). Not really his call unless the design needs to rewrite `test/config.test.ts` wholesale — then it is scope.

== 4. Strongest challenge ==

The change is framed as "make the catalog use the credential pi uses", but the extension has no way to ask pi which credential that is at the moments it matters: the factory and the poll loop hold `pi: ExtensionAPI`, which has no `modelRegistry`, and the first `ctx` arrives at `session_start`, after the startup fetch has run. So the honest implementation is not "read pi's answer" but "re-implement pi's precedence rule in `src/config.ts`" — a second copy of a policy that lives in pi-ai's `resolve.js`, which will drift the next time pi changes it (it already changed between the version the docs were written for and 1.5.2: "stored owns the provider" is a 1.5.x comment). The counter is that the copy is three lines, pinned by tests against the matrix I ran, and the alternative (defer every fetch until a `ctx` exists, or add a `refreshModels` hook so pi hands the credential over) adds mechanism and a startup ordering change to buy a guarantee the three lines already give. I would take the three lines, name them as a mirror of `resolve.js:24-38` in one place, and let the gate hold the design to "one rule, one home" inside this repository.
